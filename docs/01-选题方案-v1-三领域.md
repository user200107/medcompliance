## 5. 方案 A：`MediReg 械规通` — 医疗器械注册与出海合规知识引擎

### 5.1 定位

**给医疗器械注册专员/研发/出海团队用的注册路径知识引擎。**
输入产品描述（结构组成、材料、预期用途、接触方式），输出：

1. 建议的**管理类别**（一类/二类/三类）与**分类编码**（如 07-07 医用成像器械）
2. 需要遵循的**指导原则**清单（带条款来源）
3. **临床评价路径**：是否落在《免于临床评价医疗器械目录》里，否则走同品种比对
4. **出海对照**：同一产品在美国（510(k)/PMA）、欧盟（MDR Class I/IIa/IIb/III）的路径差异

### 5.2 核心工作流

```
产品描述 / 技术要求文档
   → 意图路由（分类判定 / 指导原则检索 / 临床评价 / 跨境对照）
   → 分类目录树检索（层级收窄）+ 指导原则混合检索
   → 图谱查询（产物类别 ↔ 指导原则 ↔ 审评要点 ↔ 免临床目录条目）
   → 生成带引用的结论 + 法规版本标注
   → 合规兜底（不得给出"一定可以注册"的确定性结论）
```

### 5.4 三个真难点（面试素材）

1. **法规版本时效治理（A 的招牌）**
   指导原则会废止、被替代、有过渡期。同一句提问"XX 产品需要做临床评价吗"，
   在 2021 版和 2023 版指导原则下答案可能相反。
   做法：知识条目带 `effective_date` / `superseded_by` / `status`，检索时按"提问时点"过滤，
   答案里强制标注"依据 XX 版，该版本已于 YYYY-MM-DD 被替代"。
   **这是 fintech-brain 完全没有的一维，也是真实注册工作的最大痛点。**

2. **分类判定必须是确定性优先**
   你已经很擅长这个模式（`services/contract.py` 的"规则库先行，LLM 增强，失败降级"）。
   分类编码走**目录树逐级收窄 + 排除法**，LLM 只负责把产品描述规范化成目录条目语言，不负责最终判定。
   面试可讲："我没有让 LLM 分类，我让 LLM 翻译用户语言，判定交给确定性树。"

3. **实体消歧比金融更难**
   公司名消歧只需别名表；器械要消歧的是**注册证号 / 型号规格 / 同品种产品**。
   注册证号有强格式，可以先正则归一，再用向量兜底——比金融那套更准，且可解释。

## 6. 方案 B：`LabelSentry 标签哨兵` — 预包装食品 / 化妆品标签合规视觉审核

### 6.0 为什么这个方案最好讲

FourfoldClarity 最大的软肋是：**"淡红舌薄白苔"到底判对没判对，谁说了算？**
没有 ground truth，就没有指标；没有指标，简历上只能写"实现了"。

而且你现在的"评测"很虚：`03_eval_dataset.sql` 只有 10 条文本，`api/admin.py::_evaluate`
做的事是**拿这 10 条去跑一遍红黄词正则**，连模型都不调用。这个"准确率"在面试里不敢报。

标签审核把它翻转过来：**必标项是可枚举的清单，判定是可以被人工复核的。**
- 有 ground truth → 能出准确率
- 有条款 → 每条判定都能指到标准原文
- 有版本 → GB 7718 正在换版，天然做出"同一张图两个结论"的硬 demo

**这个方案的本质是：把你最弱的一个项目，改造成唯一一个能出客观指标的项目。**

### 6.1 定位

**给品牌方 / 电商平台做上架前标签自检。**
上传一张预包装食品或化妆品标签照片，输出：

1. **逐项必标项检查表**（食品名称、配料表、净含量、生产者信息、生产日期、保质期、贮存条件、产品标准代号、生产许可证编号、营养成分表、致敏物质提示…）
2. 每一项判定：`合规` / `违规（附条款原文）` / `不可判定（说明缺什么）`
3. 整改建议
4. 顶部一行总风险等级 + 一行免责声明
5. **AI 结论是草稿**：审核员复核、修改、确认后才生成不可变报告快照 —— 直接继承你现有的发布门禁

### 6.2 核心工作流

```
标签照片
   → 质量预检（复用 Pillow：亮度/分辨率/模糊/倾斜）——不合格直接要求重拍，不进模型
   → 视觉模型做版面解析 + 文本抽取（区域 + 文本 + 相对位置 + 相对字号）
   → 必标项清单化：把 OCR 结果映射到标准要求的 N 个槽位
   → 逐槽位规则判定（确定性）+ LLM 只处理语义类条目（如配料表递减顺序、复合配料展开）
   → 三态结论 + 条款依据 + 整改建议
   → 输出层护栏：不得出现"该产品合法/可以上市"类断言
   → 落库为**待复核草稿**（不进用户可见结果）
   → 审核员复核/修改/确认 → 不可变快照 → 出具报告
   → 审计留痕（who did what to which data）
```

> 最后两步是你已经写好的 `api/clinical.py` 状态机（consent → 认领 → 编辑草稿 → revision CAS → 确认发布 → 不可变快照）。

### 6.4 四个真难点

1. **标准换版并存期（B 的招牌，也是最好的 demo）**
   GB 7718-2025《食品安全国家标准 预包装食品标签通则》于 2025-03-16 发布、
   **2027-03-16 实施**（[来源](https://zlzx.zjamr.zj.gov.cn/bzzx/public/news/view/analysis/6129bfbd7aca45fcb20740d18e4df72b.html)），
   与现行 GB 7718-2011 存在并存期，新增/调整了强制标示项（如致敏物质提示、日期标示方式）。
   → 系统按**生产日期**路由到适用版本，**同一张标签在两个版本下给出不同结论**。
   这是一个 30 秒就能演示、且绝不可能靠"调 prompt"糊过去的真问题。

2. **版面的物理度量**
   标准要求部分强制标示内容"在同一展示版面""字号不小于规定高度"。
   这不是文本问题，是**几何问题**：需要从图里估计 mm，或要求用户提供参照物，
   或退化成"相对字号 + 不可判定"。**敢于输出"不可判定"本身就是设计水平。**

3. **三态判定 + 拒答**
   `合规` / `违规` / `不可判定`。三态设计把"模型不确定时不许瞎判"工程化：
   OCR 置信度低、信息不在图内（如需要看背面）、图片倾斜过大 → 一律 `不可判定` 并说明原因。
   这直接呼应你在 ApplianceInsight 里写的"未命中不借用其他型号资料"——同一个工程价值观。

4. **把没接线的置信度门禁真正接上（顺手修复原项目的一个硬伤）**
   FourfoldClarity 里 `system_config.safety.image_confidence_threshold` 和 `low_confidence_note()`
   **写好了但没有任何调用方**；同时 `_parse_json` 解析失败返回 `{}`，紧接着
   `data.setdefault("confidence", 0.5)` —— **视觉识别失败被静默包装成一个"成功但为空"的识别结果，
   然后直接进入辨证**。这等于把"模型失败"变成了"临床结论"，恰好违背了你 docs 里自己写的原则。
   在 B 里必须改对：解析失败 → 抛 `AnalysisUnavailable`；`confidence < 阈值` 或
   `quality_flags` 非空 → 该槽位直接判 `不可判定`，不进判定引擎。
   **面试时这是一个极好的"我发现了自己的设计缺陷并修掉"的故事。**

## 7. 方案 C：`TariffLens 归类之眼` — 跨境商品归类与出口管制合规

### 7.1 定位

**给跨境卖家 / 报关行 / 出海企业做申报前的归类与管制初筛。**
输入产品描述（品名、材质、用途、成分、加工方式），输出：

1. HS 编码建议（国际 6 位 + 中国 10 位本国子目），**Top-3 候选 + 每条的归类依据**
2. **归类总规则（GRI 1–6）推理链**：为什么走这条子目，命中了哪条规则
3. 相似**归类决定 / 预裁定**先例（附文号）
4. 进出境监管条件、检验检疫类别、申报要素清单
5. 出口管制初筛：是否命中两用物项管制清单 / 实体清单（附命中理由与置信度）

### 7.2 为什么这个领域技术上最漂亮

- **HS 是树，不是表。** 归类必须从章 → 品目 → 子目逐级收窄，是天然的**层级约束满足 + 图遍历**，
  不是"向量搜最像的 5 条"。这跟你现有 RAG 是正交的能力。
- **归类总规则是可解释的判定规则。** 每一条结论都能说"依据 GRI 3(b) 基本特征"，
  这让你能做出**推理链**，而不是一个黑盒分数。
- **归类决定 = 天然标注集。** 海关公布的归类决定本身就是"产品描述 → 编码"的成对数据，
  你不需要从零标注就能拿到几百条 ground truth。**这是三个方案里唯一一个"标注成本≈0"的。**
- **实体筛查复用你已经写好的消歧管线。** `fintech-brain/knowledge_graph/entity_linker.py` 的
  精确命中 → 模糊 → LLM 裁决三级策略，平移到管制清单实体匹配上几乎不用改。

9. `fintech-brain/frontend/src/stores/chat.js:27` 一段乱码注释。

## 12. 简历怎么写

### 12.1 只放 3–4 个

建议保留 + 新增的组合（按你投的岗位调）：

| 岗位方向 | 放什么 |
|---|---|
| **AI 应用 / 大模型应用工程师** | 标签哨兵(B) + 归类之眼(C) + 法律平台(有微调) + fintech-brain(有可观测性) |
| **RAG / 知识工程方向** | fintech-brain + 械规通(A) + 法律平台 |
| **偏工程架构** | fintech-brain + 法律平台 + 标签哨兵（三套不同的存储与护栏设计） |
| **不建议** | 五个全放。面试 45 分钟，放五个等于每个讲 8 分钟，全部讲不深 |

**ApplianceInsight 和 paw-answer 建议合并成一条**："基于同一套多存储骨架在 2 个行业完成落地（家电售后、宠物电商）"——
这句话本身就是一个很好的迁移能力证明，占 1 行而不是 2 个项目。

### 12.2 每个项目的三行模板

```
项目名 · 一句话产品定位（给谁解决什么）
· 硬技术点 + 可量化结果（数字必须是你真跑出来的）
· 一个只有认真做过才说得出的设计取舍
· 一个边界声明（你不做什么，为什么）
```

第三条和第四条是你现有作品里已经有的优势（"确定性规则先于模型""未命中不借用其他型号资料"
"没有真实语义模型的 Recall@5"），**保持这个诚实度，它是差异化**。但要把它从"局限说明"
升级成"设计取舍"——面试官更愿意听"我为什么选择不这么做"，而不是"我没做"。

### 12.3 简历上不要出现的

- ❌ 技术栈罗列（"FastAPI, LangGraph, Milvus, Neo4j, Redis, Celery, Vue3…"）—— 五个项目都这么写，等于没写
- ❌ "实现了 XX 三阶段训练"—— 没有前后对比数字时，这是负资产（暗示只会跑脚本）
- ❌ 任何你没跑通的数字
- ❌ 与代码不符的架构描述

### 12.4 面试官一定会问的六个问题（提前写答案）

1. **"你这几个项目看起来都是 RAG + LangGraph，有什么区别？"**
   → 用第 8 节的矩阵回答：输入模态 / 算法 / 输出形态三个维度都不同，
   共同点是"模型只做翻译，判定交给确定性引擎"——这是我的方法论，不是重复。

2. **"分类准确率 __% 是怎么测的？评测集哪来的？"**
   → 说清来源（分类目录反推 / 归类决定）、样本量、是否人工标注、是否与 prompt 隔离。

3. **"为什么不让 LLM 直接输出编码/结论？"**
   → 可解释性 + 可复现 + 责任边界。LLM 输出会漂，税则树不会。

4. **"不可判定的比例 __%，是不是模型不行？"**
   → 不可判定率低但人工复核正确率也低，才是真的不行。两个数要一起看。

5. **"如果法规更新了，你的系统怎么办？"**（A/B 都会问）
   → 版本表 + 生效日期路由 + 更新只动 registry，不动引擎。

6. **"这套东西能上线吗？还差什么？"**
   → 主动说出差距（多租户、权限、真实数据授权、效果监控闭环）。
   **主动承认差距的人会被认为可靠；被问出来的人不会。**

## 13. 数据与合规边界

| 领域 | 红线 | 做法 |
|---|---|---|
| 医疗器械 | 不构成注册申报建议 | 全程标"仅供参考，以药监局审评为准"；不生成"保证获批"类结论 |

**这三条免责声明本身就是合规领域的专业性证明**——你已经有的 `DisclaimerBar.vue` 直接用。
