# 简历怎么写：把 P1 抓成主线

> 目标：一条主项目 + 一条能力佐证，让面试官在 90 秒内认定
> "这人做的是能评测的 AI 应用，不是 demo 拼装"。

## 1. 为什么选 P1 当主线

| | P1 注册路径判定 | P2 标签审核 | P3 卷宗一致性 |
|---|---|---|---|
| 数据来源 | **1,657 条官方裁决 + 1,917 节点真实目录** | 合成（缺陷人为埋入） | 合成（冲突人为埋入） |
| 指标性质 | 真实数据上的真实指标 | 引擎检出能力 | 引擎检出能力 |
| 指标规模 | n=355，带 95% CI | n=300 | n=180 |
| 技术深度 | 目录树遍历 / 时效路由 / 风险偏好 / 混合检索 | 规则表 + 三态 + 发布门禁 | 归一化 + 冲突判定 |
| 稀缺性 | **高**：公开数据里能挖出标注集的人不多 | 中 | 中 |
| 能否被证伪 | **能**：三次改进都被数据否掉 | 较弱 | 较弱 |

**决定性理由**：P1 是唯一一个"指标建立在真实数据上、且我自己能证明它还不够好"的模块。
这两点合起来，是面试里最难伪造的东西。

P2 的 100%、P3 的 100% 都来自合成集，只能证明"引擎按预期工作"，
不能证明"在真实场景有效"。**把合成集的 100% 放主线，一被追问就掉价。**

## 5. 必须准备好的三个追问

**Q1：69.6% 不高，这系统能用吗？**
> 不能直接上线，我把它定位成**评测基准 + 待改进基线**。它的价值是让后续任何改进都有参照系——
> 我试的三个方向都在它上面被否掉了。要上线，下一步是把检索式改成有监督分类，
> 因为我已经证明了瓶颈不在检索质量。

**Q2：为什么不用大模型直接判类别？**
> 试过路线，但没用模型拍板。原因有两个：一是**可复现性**——注册专员要能复算同一结论；
> 二是**可解释性**——结论必须能指到目录条目和规则。LLM 只做"口语 → 结构化槽位"这一步，
> 这一步它做得好且错了能发现。

**Q3：你的评测集怎么保证不泄漏？**
> 分类目录的「品名举例」在检索索引里，如果拿它当评测输入等于背答案——准确率会骗到接近 100%
> 然后一被问就崩。所以我用的是**分类界定结果**：那是企业送审时写的产品详情，
> 从不进任何目录，是真正的 held-out；而且送界定说明归类本身有争议，天然是难例。

## 7. 如果目标岗位偏"合规产品/质量系统"

把主线换成 P2，因为它的**发布门禁**更贴产品岗口味：

> - 把 15 条必标项做成**条款驱动的规则表**（加一项只加一行数据，判定引擎不动），
>   AI 结论一律为草稿，须审核员署名确认后生成不可变快照（revision CAS，重复确认返回 409）
> - 三态判定（合规 / 违规 / **不可判定**）：识别置信度不足只允许判"不可判定"，
>   把"看不清"和"违规"分开——前者冤枉企业，后者放过风险
> - 合成集上缺陷检测 P/R 100%（结构化输入）/ 召回 80%（文本输入）；两者 20pp 差距
>   量化了视觉抽取层缺失的影响

主线换了，但第 2 节里的"数据底座 + 三层评测"仍然要挂在 P1 条目上作为佐证，
因为那是唯一有真实数据支撑的部分。

## 9. 拆成三个：按「套件 + 三模块」写，而不是「三个独立项目」

### 三种写法的对比

| | 篇幅 | 信号 | 风险 |
|---|---|---|---|
| **A. 一主线 + 两佐证**（§2/§4） | 5 行 | "有一个深的主攻方向" | 模块名不突出 |
| **B. 一套件 + 三模块**（本节） | 8–9 行 | "三个东西 + 一个平台" | 略散，需一句防拆穿 |
| **C. 三条独立项目** | 15 行 | "三个独立产出" | 技术栈重复三次；P2/P3 被单独追问真实数据；丢掉"底座复用"信号 |

**C 通常最差**，原因具体：

1. 三条都要写技术栈 → 同一套 `FastAPI/Pydantic/DashScope` 重复三次，读者会当成凑数；
2. 每条都会独立被问"真实数据上的准确率多少" → P2/P3 只能答"合成集"，
   而在 A/B 写法里它们躲在 P1 的真实数据条目后面，不会被单独拷问；
3. 丢掉最有价值的信号——**"同一套法规底座复用三次"**。三个独立项目听起来像做了三遍，
   一个套件听起来像设计了平台。

关键点：**套件标题承载"共享底座"，三个模块各带一个自己的数字或设计取舍。**
这样既拿到三个名字，又没有把底座拆成三份谎话。

### 前提：你不能同时放 8 个项目

你手上已有 5 个旧项目（投研 / 中医 / 法律 / 家电售后 / 宠物电商）。
拆成三模块后，**旧项目最多留 1–2 个**。

简历上 3–4 个项目是上限。8 个项目 = 面试时每个只有 5 分钟，全都讲不深。
建议：`medcompliance（三模块）+ 法律平台（有微调）+ 投研大脑（有可观测性）`，其余合并成一行
"另有两个基于同一多存储骨架的行业落地（家电售后 / 宠物电商）"。

### 准备一句防拆穿的话

面试官很可能问："这三个是不是把一个项目拆成三个？"

> 不是拆，是共用底座后各自独立部署。分类目录树、法规版本时效、产品主数据在一个包里，
> 三个服务各自有自己的 Dockerfile 和评测集，可以单独交付——
> 底座的代码复用率大概七成，但领域层和失败模式完全不同：
> 一个是答错，一个是漏看标签，一个是对不上数据。

这句话的杀伤力在最后一句：**三种失败模式不同，是"三个应用"最硬的证据。**

### 什么时候 C（三条独立项目）才成立

只在这三种情况下：

1. 你投的是**解决方案 / 售前 / 咨询**岗，看重覆盖面而不是单点深度；
2. 简历篇幅充裕，且你愿意为这三条准备、把其他 5 个项目全砍；
3. 每条都能给出**不同的真实数字**（目前只有 P1 有，所以现在不满足）。

否则用 B。

## 10. 完整项目经历（五段式：背景 / 技术栈 / 职责 / 解决方案 / 成果）

> 下面这块按标准简历的"项目经历"结构写，可直接粘贴。
> **两处需要你替换**：起止时间（`2026.XX`）与"独立完成"的表述（若你有团队背景，改成对应的角色）。

### 医疗器械合规智能体套件

**个人项目｜2026.XX – 2026.11｜独立完成**

#### 一、项目背景

医疗器械注册的第一步是确定**管理类别**（Ⅰ / Ⅱ / Ⅲ 类），它直接决定注册路径——
Ⅰ 类备案、Ⅱ 类省级注册、Ⅲ 类国家局审评。**判错不是"稍微不准"，而是整条流程走完再被打回。**

现实做法是注册专员翻《医疗器械分类目录》（22 个子目录、1,689 个可定类条目）+
逐份查指导原则 + 靠经验判断。人肉检索慢、易漏，且不同人对同一条目录的解读不一致。

而通用大模型在这个场景直接不可用：它会编造不存在的分类编码、引用已废止的指导原则，
且结论无法复算——注册场景对"可追溯、可复现"的要求比"答得漂亮"高得多。

**我要解决的是**：把公开法规做成一个可检索、可推理、**且可评测**的知识底座；
用确定性规则承担判定，模型只负责语言转换；并建立评测口径回答"它到底行不行"。

#### 二、技术栈

`Python 3.12` · `FastAPI` · `Pydantic v2` · `SQLAlchemy 2`（ORM + 内存 SQLite 验证）
· `numpy`（内存向量索引与余弦检索）· `httpx`
· 检索：字符 n-gram / BM25 + 稠密向量 + 交叉编码器重排（两段式）
· 模型：`qwen-plus`（槽位抽取）· `text-embedding-v4`（1024 维）· `qwen3-rerank`
· 工程：Docker Compose（三服务编排）· pytest（171 个测试）· 原生 HTML/CSS/JS 前端（零构建）

> 注：这里刻意没有用向量数据库与图数据库——目录只有 1,917 个节点，
> numpy 内存索引足够，引入 Milvus/Neo4j 是过度设计。

#### 三、项目职责

**独立完成全链路**：产品定义 → 公开数据获取与清洗 → 领域建模 → 判定引擎 → 评测体系 → 服务与前端。

主攻**注册路径判定模块**（分类目录树 + 法规版本时效 + 判定流水线 + 风险偏好策略），
另外两个模块（标签合规审核、卷宗一致性审查）复用同一套法规底座扩展而来。

#### 四、解决方案

**1）领域建模：把"法规会过期"做成一等公民**
抽象六个实体：分类目录节点、产品、注册证、监管文件、**文件版本**、条款。
把「指导原则/标准」只在版本层区分（`kind` + `version`），条款挂在版本上。
关键取舍：`status` 描述的是"**现在**"，而检索要按"提问时点"判定——
一个今天已废止的版本，在 2019–2023 的窗口里就是当时的现行版。
所以版本有效性只认日期窗口，`status` 仅用于排除征求意见稿。

**2）判定与推理分离：模型只做翻译**
七阶段确定性流水线：槽位抽取（唯一调 LLM 的环节）→ 前置闸门（是否属于医疗器械）→
子目录粗筛 → 类注排除 → 叶子匹配 → 规则裁决 → 输出 Top-K + 依据链。
分类编码由目录树逐级收窄得出，不由模型生成——这是可复现与可解释的前提。

**3）风险偏好显式化，而不是埋在阈值里**
判低与判高代价不对称（Ⅱ 类走省级、Ⅲ 类走国家局），所以"取最高分"并非天然正确。
做成 4 档可配置策略（α 带宽内「就高不就低」），用成本矩阵（判低 3 / 判高 1）评测，
策略名随结果回传，同一问题换策略得出不同类别时可解释原因。

**4）建立三层评测口径**
- 端到端：544 条分层抽样，报覆盖率 / Top-1 / Top-3 / 拒答率，带 Wilson 95% 区间；
- 检索层隔离：绕过槽位抽取直接测目录检索，用于区分"抽不出来"与"判错了"；
- 合成集：P2 缺陷检测、P3 冲突检测，用于测引擎能力（明确标注非真实准确率）。

数据侧解决"没有标注"：从药监局公开的 6,434 条**分类界定结果**中抽取 1,657 条作评测集。
选它的理由是可验证的——分类目录的「品名举例」在检索索引里，拿它当输入等于背答案；
而界定结果的产品详情是企业送审原文，从不进任何目录，是真正的 held-out。

**5）工程化**
单仓库四包：`domain`（共享底座）+ 三个独立服务（各自 Dockerfile 与评测集）。
CORS 只放行本地演示来源；AI 结论一律为草稿，对外报告须审核员署名确认后冻结为不可变快照。

#### 五、项目成果

- **数据资产**：1,703 条公开分类目录 → **1,917 节点树**（1,689 个可定类，完整性校验零问题）；
  自建 **1,657 条官方裁决评测集**（19 个公告批次，2019–2026）
- **效果**：端到端覆盖率 **77.4%**；355 条可判定样本上类别 Top-1 **69.6%**（95% CI 64.6–74.1，
  Macro-F1 0.669）；检索层隔离实验（451 条）Top-1 62.3%，多数类基线 45.2%
- **关键判断**：用同一台评测机证伪了三条改进路线（层级约束 / 交叉编码器重排 / 稠密向量）——
  三者都把 Ⅲ 类召回抬高约 12pp，代价是 Ⅰ 类召回从 74.6% 塌到 31.1%。
  据此判定**瓶颈不在检索质量，而在"管理类别不是文本相似度的函数"**，转向有监督分类方向
- **可复用**：同一底座扩展出标签合规审核（15 条条款驱动规则 + 三态判定 + 发布门禁）
  与卷宗一致性审查（6 类属性归一化 + 三态冲突判定），三者共用底座、独立部署
- **质量**：171 个自动化测试；评测脚本可复跑（数据指纹 SHA-256 + 分层抽样固定 random seed）

#### 使用说明

1. **"独立完成"要按真实情况改**。这是个人项目，写"独立完成全链路"是准确的；
   如果你在工作场景里做过类似的事，可以并入工作经历，但别把个人项目写成团队项目。
2. **不要加"效率提升 X%"这类数字**。没有线上对照数据，编一个反而会被追问穿。
3. **Ⅲ 类召回 43.6%、视觉抽取未接、门控特异度 4.3%** 这三条短板要主动说，
   手册 §6 已写好话术——**主动承认边界比藏起来安全**。
4. 面试顺序建议：先讲背景（30 秒）→ 直接讲"我做了什么判断"（第四段的关键取舍）→
   最后用数字收尾。**不要从技术栈开始讲。**

### 11.3 只给 6 行怎么砍

按这个顺序丢：

1. 先砍**技术栈那一行**（简历顶部若已有技能栏，它就是冗余的）
2. 再砍**"已知短板"那一行**（挪到面试口头说，别占简历）
3. 最后才动数字行——**数字行是最后才能砍的**，没有数字的项目等于没做

剩下的骨架是：标题 / 背景 / 数据资产 / 判定取舍 / 效果数字 / 关键判断。

### 11.4 两条不能砍

无论压到几行，这两条必须留：

- **可核对的效果数字**（含 n 与区间，或至少含基线）——没有它，整条项目退化成功能罗列
- **那条判断**（"因此判定瓶颈不在检索…"）——它区分"执行者"和"能定义问题的人"

其余都可以按篇幅删。
