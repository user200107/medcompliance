# 同一垂直领域：从一个项目群到"行业纵深"

> 这是 v1 的替代方案。v1（三领域）里的模块映射、难点分析、指标设计仍然有效，可直接复用；
> 本文只回答新问题：**把三个项目放进同一个行业，怎么放才能不只是"复读三遍"。**

---

## 0. 结论

**垂直领域：医疗器械（RA / QA 合规）。**

一句话叙事：**「医疗器械合规智能体套件」——一个法规知识底座，三个应用，覆盖产品从分类、到标签、到注册申报的三个必经环节。**

| | 产品名 | 干什么 | 用户 | 承接 |
|---|---|---|---|---|
| **P1** | `MediReg` 械规通 | 问：我这类产品走什么注册路径、要交什么资料 | 注册专员 / 研发 | fintech-brain |
| **P2** | `LabelGuard` 标签哨兵 | 看：这张标签/说明书能不能过 | QA / 质量部 | FourfoldClarity |
| **P3** | `DossierReview` 卷宗审查 | 审：这套申报资料缺什么、哪儿自相矛盾 | RA 顾问 | legal_project |

**为什么医疗器械是唯一一个三项都成立的选择**（见 §2）：它同时具备
① 海量长文档（指导原则、分类目录、标准库）② 可逐项枚举的视觉合规判定（标签必标项）
③ 跨文档一致性是行业公认的痛点（型号规格不一致是发补重灾区）。

## 1. 换思路意味着什么

| | v1：三个行业三个项目 | v2：一个行业三个产品 |
|---|---|---|
| 叙事 | "我做过很多行业" | "我吃透一个行业" |
| 面试官观感 | 广但浅；五个项目都像 demo | 深；有平台化思维；能对话 |
| 最大风险 | **重复感**——第五个 RAG 全栈 | **一个产品拆成三个**——看起来在为项目数注水 |

单领域方案的风险更隐蔽也更致命：面试官会觉得你在拿同一套东西骗项目数。

### 1.1 三条防重复原则（贯穿全文，必须守住）

1. **不同岗位、不同权限**。注册专员 / QA / RA 顾问在真实器械公司是三个部门，
   权限和工作流天然不同。这是最强的"不是同一个东西"的证据。
2. **不同输入模态、不同失败模式**。
   - P1 失败是**答错**（引用了已废止的指导原则）
   - P2 失败是**漏看**（标签上少了 UDI，系统没发现）
   - P3 失败是**对不上**（技术要求写 Ø3.2mm，检验报告写 Ø3.5mm，系统没发现）
   三种失败模式互不覆盖，这决定三个应用的技术栈必然不同。
3. **共享的是"库"，不是"应用"**。底座是一个领域服务（法规版本 + 产品主数据 + 检索），
   三个应用各自独立部署、独立评测、可以单独卖给客户。

## 2. 为什么是医疗器械

新标准不是"热不热"，而是**这个领域能不能同时喂饱三种形态**。

| 候选 | 长文档知识体 | 可枚举视觉判定 | 跨文档一致性 | 数据公开 | 行业势能 | 责任边界清晰 | **合计/30** |
|---|---|---|---|---|---|---|---|
| **医疗器械** | 5 | 5 | 5 | 5 | 5 | 5 | **30** |
| 跨境贸易 | 5 | 3 | 4 | 5 | 5 | 4 | 26 |
| 化妆品 / 日化 | 4 | 5 | 4 | 5 | 3 | 4 | 25 |
| 食品 | 4 | 5 | 3 | 5 | 3 | 4 | 24 |
| 工程建设 | 4 | 4 | 3 | 3 | 4 | 4 | 22 |
| 保险理赔 | 4 | 4 | 4 | 2 | 4 | 3 | 21 |
| 汽车后市场 | 3 | 5 | 3 | 2 | 4 | 3 | 20 |
| 家电售后（已做） | 3 | 3 | 2 | 2 | 2 | 3 | 15 |

**医疗器械拿满分的三个具体原因：**

- **P2 的判定标准是可枚举的法定清单**。《医疗器械说明书和标签管理规定》
  规定了应当标注的内容，加上 YY/T 0466.1（ISO 15223-1）的图形符号 —— 判定表能一行行写出来。
- **P3 的对照表是官方给的**。《医疗器械注册申报资料要求和批准证明文件格式》
  （2021 年第 121 号通告）本身就是一套 **RPS 章节化目录**（监管信息 / 综述资料 / 非临床资料 /
  临床评价资料 / 说明书和标签样稿 / 质量管理体系文件）。
  → "缺项审查"不需要你发明标准，只需要你**按官方目录核对**。这是作品集里最稀缺的属性：**你的评估标准是权威的，不是你自己编的。**
- **数据全公开**。器审中心指导原则文本库、分类目录、免临床目录、FDA 510(k) 数据库、EU MDR。

> 备选：如果嫌医疗器械离你已有的中医项目太近（其实不近——一个是临床诊疗，一个是法规合规），
> 换成**化妆品/日化**：同一套套件结构完全成立（法规库 + 标签审核 + 配方/宣称合规审查），
> 只是产业势能和客单价低一档。§10 给了替换说明。

## 3. 套件架构

```
┌──────────────────────────────────────────────────────────────┐
│  横切：统一账号与角色 / 审计留痕 / AI 草稿→人工确认门禁 / 可观测   │
└──────────────────────────────────────────────────────────────┘
        │                    │                      │
┌───────▼──────┐   ┌─────────▼───────┐   ┌──────────▼───────┐
│ P1 MediReg   │   │ P2 LabelGuard   │   │ P3 DossierReview │
│ 注册路径问答  │   │ 标签视觉审核     │   │ 申报资料审查      │
│ 文档 → 答案   │   │ 图片 → 检查表    │   │ 文档集 → 审查报告 │
└───────┬──────┘   └─────────┬───────┘   └──────────┬───────┘
        └────────────────────┼──────────────────────┘
                   ┌─────────▼──────────────────────────┐
                   │  共享「法规知识底座」               │
                   │  · 法规/标准/条款 + 版本时效        │
                   │  · 产品主数据（产品/注册证/分类编码）│
                   │  · 混合检索（向量+BM25+RRF+rerank） │
                   │  · 图谱（分类目录树 + 产品—标准关系）│
                   └────────────────────────────────────┘
```

### 3.1 共享层（一次建，三处用）—— 这才是"相关性"的真实来源

**领域模型**（新建 `domain/`）：

| 实体 | 关键字段 | 谁用 |
|---|---|---|
| `Product` | 名称、型号规格[]、结构组成、预期用途、接触方式、材料 | 三个都用 |
| `ClassificationCode` | 分类编码、名称、父级路径（01-01…） | P1 判定、P3 核对 |
| `RegistrationCert` | 注册证号、有效期、型号、结构组成 | P1 检索、P2 校验、P3 核对 |
| `Guideline` | 名称、文号、发布日、实施日、**status（现行/废止/被替代）**、superseded_by | P1 主用 |
| `Standard` | 标准号（GB/YY）、版本、状态 | P1、P2 |
| `Clause` | 条款号、原文、所属法规版本 | 三个都用（引用溯源） |

**这一层是三个应用真正的技术耦合点**，不是话术：
P1 产出"这个产品属于 07-07，适用这些指导原则" → 写入 `Product`；
P2 拿 `RegistrationCert` 校验标签上的注册证号对不对；
P3 拿 `Product.models[]` 去核对技术要求、说明书、检验报告里的型号是否一致。

### 3.2 各应用独有

| | P1 独有 | P2 独有 | P3 独有 |
|---|---|---|---|
| 输入 | 产品描述 / 技术要求 | 标签或说明书图片 | 一套申报资料（多文件） |
| 核心算法 | 分类树遍历 + 混合检索 + 时效路由 | 视觉抽取 + 必标项规则引擎 + 版面度量 | 结构化抽取 + 跨文档实体对齐 + 冲突检测 |
| 输出 | 带引用长答案 | 逐项检查表（三态） | 审查报告（缺项 + 冲突） |
| 独有依赖 | 图谱 | 视觉模型 | 微调（LoRA） |
| 评测集 | 200 条分类判定 | 200 张标签图 | 30 套合成卷宗 |

## 4. 三个产品

### 4.1 `P1 MediReg 械规通` —— 注册路径知识引擎

**承接 fintech-brain。**

**用户问题**："我这个产品是几类？走什么路径？要不要做临床评价？要交哪些资料？"

**输出**
1. 建议**分类编码**（如 07-07）+ 命中的目录条目原文
2. 适用**指导原则清单**，每条标注发布日 / 现行状态
3. **临床评价路径**：是否落入《免于临床评价医疗器械目录》，否则走同品种比对
4. **RPS 资料清单**：按 121 号通告的章节，列出本项目需要准备哪些
5. 出海对照：FDA 510(k) / EU MDR 分类与路径差异

**难点**
- 分类判定必须**确定性**：目录树逐级收窄 + 类注排除，LLM 只把用户语言规范化成目录语言，不拍板
- **法规版本时效**：同一问题在旧版/新版指导原则下答案可能相反 → 按提问时点过滤 + 强制标注版本
- **实体消歧**：注册证号（`国械注准2024xxxxxx`）有强格式，先正则归一再用向量兜底

**指标**：分类编码 Top-1 / Top-3（N=200）；指导原则 Recall@5（N=100）；**已废止版本引用率 → 目标 0**

**模块映射**：见 v1 §5.3（改约 10 个文件，基础设施不动）

---

### 4.2 `P2 LabelGuard 标签哨兵` —— 标签 / 说明书视觉审核

**承接 FourfoldClarity。**

**用户问题**："这张标签能不能过？缺什么？"

**输出**
1. **逐项必标项检查表**（依《医疗器械说明书和标签管理规定》+ YY/T 0466.1 符号）
   —— 产品名称型号、注册人/备案人名称地址联系方式、注册证编号、生产许可证编号、
   生产日期/失效日期、储存条件、**UDI**、灭菌方式、一次性使用标识、警示符号…
2. 每项三态：`合规` / `违规（附条款原文）` / `不可判定（说明缺什么）`
3. **机器可校验项直接校验**：注册证号格式 + 与 `RegistrationCert` 主数据比对；
   UDI 的 DI 段是否为合法 GS1 结构
4. 整改建议 → **落为草稿** → 审核员复核确认 → 不可变报告快照

**为什么这是三个里最好的 demo**：拍照 → 30 秒 → 一张红黄绿的检查表 + 每项指到条款。
不需要解释背景，任何人都能看懂。

**难点**
1. **版面度量**：法规要求标示"清晰可辨""显著"，符号有最小尺寸。
   这是**几何问题不是文本问题**：要么从图里估计 mm（需参照物/DPI），要么退化成"相对字号 + 不可判定"。
   **敢输出不可判定本身就是设计水平。**
2. **视觉失败不得变成合规结论（修 FourfoldClarity 的硬伤）**
   现状：`_parse_json` 失败返回 `{}`，紧接着 `setdefault("confidence", 0.5)` —— 识别失败被静默包装成
   "成功但空"，然后直接进入判定。同时 `safety.image_confidence_threshold` 和 `low_confidence_note()`
   **写好了但没有任何调用方**。
   在 P2 里必须改对：解析失败 → 抛 `AnalysisUnavailable`；`confidence < 阈值` 或 `quality_flags` 非空
   → 该槽位直接 `不可判定`，不进规则引擎。
3. **符号识别**：YY/T 0466.1 是图形符号（无菌、一次性使用、不得重复灭菌…），
   需要小目标检测 + 符号库匹配，不能只靠 OCR。

**关键资产：保留人工发布门禁**
`api/clinical.py` 那套（consent → 认领 → 编辑草稿 → revision CAS → 行锁 → 不可变快照 → 审计）
在 P2 里换成「审核员 / 品牌方或生产方」的角色关系，机制几乎零改动。
**这是你整个作品集里最难得的一个机制，绝对不能丢。**

**指标**：必标项漏检率（最关键——漏检比误报严重）；违规项判定 P/R；不可判定率（配合人工抽检看，虚低说明在瞎判）；符号识别准确率

---

### 4.3 `P3 DossierReview 卷宗审查` —— 跨文档一致性与完整性审查

**承接 legal_project。**

**用户问题**："这套申报资料能不能交？缺什么？哪儿自相矛盾？"

**输入**：一套申报资料 —— 产品技术要求、研究资料、临床评价报告、说明书和标签样稿、检验报告

**输出**
1. **缺项清单**：按 RPS 章节（CH1…CH3.x）核对，标注"应提交未提交"
2. **一致性冲突表**：型号规格、性能指标、有效期、灭菌方式、结构组成，
   在"技术要求 vs 说明书 vs 检验报告"三处是否一致
3. 每条结论附 **文件名 + 章节 + 原文片段**
4. 严重度分级 → 人工确认

**为什么这个最难也最有价值**：它**不是检索问题**。
RAG 能回答"技术要求里写了什么"，但回答不了"技术要求写 Ø3.2、检验报告写 Ø3.5，谁对？"
—— 必须先把多份文档抽成结构化字段，再做对齐与比对。

**难点**
1. **跨文档实体对齐**：同一个型号在五份文件里有五种写法（`A-100`、`A100`、`型号A-100`、`A-100型`）
   → 归一化 + 对齐 + 冲突判定，这和你 `fintech-brain/knowledge_graph/normalizer.py` 是同一个问题的升级版
2. **引用必须定位到"文件 + 页/章节 + 原文"**，且前端能高亮跳转 ——
   直接复用 legal_project 的 `ContractHighlight.vue` 交互
3. **微调要变成一次可证伪的实验**：不要再跑一遍 PT/SFT/DPO 三阶段（那在简历上不加分），
   而是「基座 zero-shot vs LoRA SFT」在 200 条审评要点问答上的准确率对比，报一个 `+X pt`

**指标**：缺项召回率（最看重漏报）；冲突检测 P/R；引用定位准确率；微调前后 delta

## 5. 怎么让它"看起来相关"——五个具体动作

这部分决定了套件是不是真的成立，而不是三份代码放在一个目录里。

1. **一个"产品档案"页面串起三者**
   `产品 → 分类编码 & 适用法规（P1）→ 标签审核记录（P2）→ 申报资料审查报告（P3）`
   一屏就能讲完整个故事，这是你面试时唯一需要展示的页面。

2. **共享产品主数据，形成真实的数据流**
   P1 写入产品与分类 → P2 用它校验注册证号 → P3 用它核对型号一致性。
   **这是代码级的耦合，不是叙事上的耦合。** 面试官一翻代码就能看到。

3. **统一的工程主张**
   "模型只做翻译，判定交给确定性引擎" + "AI 出草稿，人确认才发布"。
   三个应用都遵守同一条原则 —— 这从"三个项目"升级成"**一套方法论**"。

4. **统一的命名与视觉**
   套件名 `MedCompliance Suite`，三个模块 `Ask / Check / Review`。
   同一套 UI 框架、同一套评测报告模板。

5. **一个总 README + 三张图**
   总图（套件架构）、数据流图（产品主数据如何串起三者）、演进图（三个月的里程碑）。
   面试前 3 分钟看这三张图就能问出好问题。

## 6. 实施顺序（不要三个并行）

| 阶段 | 内容 | 周期 | 产出 |
|---|---|---|---|
| **W1–2** | **法规知识底座**：`domain/` 领域模型 + 法规版本表 + 混合检索 + 分类树图谱 + 审计门禁 | 2 周 | 三个应用都能调的服务 |
| **W3–5** | **P1 MediReg** | 3 周 | 分类 Top-3 准确率 |
| **W6–8** | **P2 LabelGuard** | 3 周 | 必标项漏检率 + 最强 demo |
| **W9–12** | **P3 DossierReview**（含 LoRA 实验） | 4 周 | 冲突检测 P/R + 微调 delta |

**为什么是这个顺序**（顺序错了会返工）：
- 底座先做，因为它同时是 P1 的检索层、P2 的主数据、P3 的对齐基准
- P1 第二，因为它最快验证底座（且顺带把产品主数据填起来）
- P2 第三，因为它**依赖 P1 产出的 `RegistrationCert` 才能做注册证号校验**
- P3 最后，因为它**依赖 P1/P2 抽出的结构化实体**做跨文档对齐

**如果时间只剩 8 周**：做底座 + P1 + P2，P3 降级为 MVP
（只做 RPS 章节完整性 checklist + 型号一致性这一条冲突规则，不跑微调）。
**8 周也已经是一个完整的套件故事（知识 + 视觉），比三个半成品强得多。**

## 7. 自检清单：这像三个产品，还是一个产品拆三个？

交付前逐条问自己，任何一条答"否"就要重新设计：

- [ ] 三个应用服务**不同岗位**吗？（注册专员 / QA / RA 顾问）
- [ ] 三个应用的**权限模型**不同吗？（QA 不能看全卷宗；顾问能看不能改主数据）
- [ ] **输入模态**不同吗？（长文档 / 图片 / 多文件集合）
- [ ] **失败模式**不同吗？（答错 / 漏看 / 对不上）
- [ ] 各有**独立的评测集和指标**吗？
- [ ] 任何一个能**单独交付**给客户吗？（能 —— RA 咨询公司会单独买 P2 或 P3）
- [ ] 共享的是**领域服务**，而不是"同一个 application 里的三个 router"吗？

最后一条最关键。如果你的目录结构是 `backend/app/api/{medireg,label,dossier}.py`，
那就是一个应用；如果是 `services/{domain,p1,p2,p3}` + 三个 compose，才是套件。

## 8. 简历怎么写

### 8.1 不要写成三个并列项目

❌ 错误写法（读起来像凑数）：
```
医疗器械注册知识引擎
医疗器械标签审核系统
医疗器械申报资料审查系统
```

✅ 正确写法（读起来像一个方向）：

### 8.2 条目结构：1 条套件 + 3 条模块

> **医疗器械合规智能体套件**（个人项目）｜Python · FastAPI · LangGraph · Milvus · Neo4j · Vue3

> - **MediReg（注册路径问答）**：分类目录树确定性收窄 + 类注排除，分类编码 Top-3 准确率 **__%**（N=200）；
>   检索按提问时点过滤版本，已废止版本引用率 **0/100**
> - **LabelGuard（标签视觉审核）**：视觉模型只做版面与符号抽取、判定走确定性规则引擎，
>   必标项漏检率 **__%**、UDI/注册证号机器校验准确率 **__%**；AI 结论经审核员确认后生成不可变报告
> - **DossierReview（申报资料审查）**：跨文档实体对齐检出型号/性能指标冲突，冲突检测 F1 **__%**；
>   LoRA SFT 使审评要点问答准确率 **+__ pt**

**四条 bullet，一条讲平台、三条讲应用，主线清晰。** 比五个项目并列强得多。

## 9. 数据与合规边界

| 项 | 做法 |
|---|---|
| 法规文本 | 器审中心指导原则库、121 号通告、分类目录、免临床目录 —— 全部公开 |
| 标签图片 | **自己设计/打印合成标签**拍摄最安全；避免真实产品标签的商标与版权 |
| 申报卷宗 | **合成本**：虚构一个产品（如"一次性使用无菌注射器"），自己编一套卷宗，故意埋 20 处冲突 |
| 免责 | 全程标"仅供参考，最终以药监部门审评结论为准"；不生成"保证获批"类表述 |
| 患者/用户数据 | 本项目完全不涉及 |

> 合成卷宗这件事本身就是加分项：**"我为了评测，自己造了一套带已知错误的卷宗"**
> 体现了你有构建 ground truth 的能力 —— 这正是你现有项目最缺的。

## 10. 如果换成化妆品 / 日化

同一套架构可以整体平移，对应关系：

| 医疗器械 | 化妆品对应物 |
|---|---|
| P1 注册路径（分类编码） | 产品分类（普通/特殊化妆品）+ 备案 vs 注册路径 |
| P2 标签审核（第 6 号令 + YY/T 0466） | 标签审核（《化妆品标签管理办法》必标项） |
| P3 申报资料审查（RPS） | 备案资料审查（配方、执行标准、检验报告一致性） |
| 法规库 | 《化妆品监督管理条例》《安全技术规范》《已使用化妆品原料目录》 |

代价：产业势能与客单价低于医疗器械；收益：法规资料更短，2 周能跑通。
**除非你对化妆品行业更有兴趣，否则不建议换。**
