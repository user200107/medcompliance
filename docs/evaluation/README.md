# 评测方法与当前结果

> 这份文档回答一个问题：**在没有任何人工标注预算的前提下，怎么得到一个可信的效果数字。**

---

## 1. 数据来源：官方已经替你标好了

[医疗器械分类界定结果汇总](https://app.nidc.org.cn/biaogzx/dataGk.do?formAction=listFljdResult)
（中国食品药品检定研究院公开查询，共 6,434 条）

| 字段 | 作用 |
|---|---|
| 产品名称 + 产品详情 | **输入**：企业自己写的组成与预期用途 |
| 产品类别 | **标签**：官方裁决结论 |
| 标题 + 发布日期 | 批次与时间 |

一条记录就是一条 `(X, y)`。**不需要标一条。**

### 为什么不用分类目录的「品名举例」

目录里每个类别都挂着若干品名举例，看起来也是现成的 `(名称 → 编码)` 对，成本更低。
但它有一个致命问题：

> 检索索引 `search_blob` 本身就包含 `examples`。
> 拿 examples 当评测输入 = **在测模型能不能背出自己索引里的内容**。
> 准确率会漂亮到接近 100%，然后面试官一问「评测集和索引有重叠吗」就崩。

而界定结果的「产品详情」是企业送审时写的原文，**从不进任何目录**，是真的 held-out。

### 另一个好处：它天然是难例

产品被送去界定，说明归类本身有争议。随机抽 200 条普通产品，测不出系统的边界在哪。

## 1.5 分类目录：同样不用下载

分类目录不能靠人工下载整理。但同一个站上有一个**结构化的目录库**：

[分类目录库](https://app.nidc.org.cn/biaogzx/dataGk.do?formAction=listFlmlk)
（1,703 条，10 条/页，171 页）

| 字段 | 内容 |
|---|---|
| 子目录 | `01 有源手术器械`（共 22 个） |
| 一级产品类别 | `01 超声手术设备及附件` |
| 二级产品类别 | `01.1 超声手术设备` |
| 产品描述 / 预期用途 | 判定树要匹配的语义文本 |
| 品名举例 | 检索语料 |
| 管理类别 | `Ⅰ` / `Ⅱ` / `Ⅲ` ← **标签** |

`scripts/crawl_catalog.py` 抓下来并转成 `catalog_loader` 认的 CSV：

```bash
python scripts/crawl_catalog.py --all --delay 1.0 --csv data/raw/catalog_real.csv
```

结果：**1,703 条 → 1,917 个节点**（22 子目录 + 206 一级 + 1,689 个可定类叶节点），
树完整性校验**零问题**。管理类别分布：Ⅱ 813 / Ⅰ 464 / Ⅲ 412。

### 编号陷阱

官方三段编号**每段都从 1 重新开始**：一级在自己的子目录内编号，二级在自己的一级内编号。
所以同一段编号在不同父节点下会重复。转换时拼成 `01` / `01-01` / `01-01-01.1`
才能保证全局唯一——这正好落在 `ClassificationCode` 的自引用树上，不用改模型。

### 为什么还需要官方原始文件

归档与版本溯源用。官方原文在《总局关于发布医疗器械分类目录的公告》
（[2017 年第 104 号](https://www.nmpa.gov.cn/xxgk/ggtg/ylqxggtg/ylqxqtggtg/20170904150301406.html)，2018-08-01 施行）的附件里，
之后历次调整各有公告。**留档可以，但不必用它喂程序**——附件是 Word/PDF，
要自己处理跨页断行和合并单元格，而目录库是同一份内容的结构化视图。

## 2. 合规边界（这条不能省）

站点页脚声明「未经许可禁止转载或建立镜像」。因此：

| 做 | 不做 |
|---|---|
| ✅ 本地抓取，仅用于评测 | ❌ 提交原始数据到仓库 |
| ✅ 提交抓取脚本（含限速） | ❌ 对外发布数据集 |
| ✅ 提交**指纹**（记录数 / SHA-256 / 时间范围 / 批次） | ❌ 建立镜像站 |
| ✅ 提交聚合指标 | ❌ 逐条复述原文 |

`data/raw/` 已在 `.gitignore` 中。仓库里能证明「确实跑过」的，是报告里的指纹：

```
全量记录：1657   公告批次：19
时间范围：2019-02-18 → 2026-08-06
SHA-256：5abd6ede6da7841ddf9a1344a534fcfe3eb95142393daef1aee994d6ad223db7
```

抓取脚本默认请求间隔 1.2 秒，带退避重试与断点续抓。**别把 delay 调小。**

### 抽样方式：等距，不是取前 N 条

站内按发布时间正序排列。只抓前 160 页会得到一个「全是 2019 年」的偏样本。
脚本用 `--sample-every 4` 从第 1 页到第 644 页等距取，覆盖全部年份与公告批次。

## 3. 标签空间比系统输出空间大（这是要量化的东西）

实测官方数据里出现过 **7 种**原文结论：

| 原文 | 归一化 | 系统能否产出 |
|---|---|---|
| `Ⅲ` / `Ⅱ` / `Ⅰ` | CLASS_III / II / I | ✅ |
| `不作为医疗器械` | NOT_A_DEVICE | ✅ |
| `不单独作为医疗器械`、`建议不单独申报` | NOT_ALONE | ❌ |
| `药械组合` | COMBINATION | ❌ |
| `视具体情况而定` | DEPENDS | ❌ |
| 其他（如 `建议不按照医疗器械管理`） | NOT_A_DEVICE / OTHER | 部分 |

所以代码里是**两个枚举**：

- `ClassificationOutcome` —— 系统**能产出**的 4 种
- `ExpectedOutcome` —— 数据里**存在**的全部标签

系统表达不了的样本（本轮 157/1657，9.5%）**从指标中排除并单独计数**，
而不是硬塞进某一类去凑准确率。

> `视具体情况而定` 特别值得说：**连监管机构都不给唯一结论**。
> 要求系统在这些样本上给出确定答案，本身就是不公平的评测。

## 4. 指标口径

### 4.1 门控：默认视为器械 → 必须报特异度

闸门的实际策略是「没有确定性否定表述就默认视为器械」。这是运营上合理的
（不可能把所有产品都拒答），但代价必须量化：

```
准确率 83.6%  ← 看着还行
特异度  4.3%  ← 真实水平
```

因为数据里器械占 82.9%，**把所有样本都判成器械就能得到 82.9% 的准确率**。
门控只比这个多数类基线高 **+0.7pp** —— 等于没有提供信息。

这就是为什么报告里必须并排放「多数类基线」。只报准确率等于自欺。

### 4.2 类别：只在给出结论的样本上算，覆盖单独报

拒答（转追问）既不是对也不是错。把它算成错答，会把两个完全不同的问题
（覆盖不足 / 判错）混成一个数字，而它们的改进路径完全相反。

所以：
- **准确率** = 在 `status == classified` 的子集上算，带 Wilson 95% 置信区间
- **覆盖率** = 给出结论 / 总样本，单独报
- 两者必须一起看：coverage 很低时，任何准确率都不值得看

### 4.3 样本数与置信区间

n=544 时 95% 区间约 ±3pp；n=200 时约 ±7pp。
报告里所有比例都带区间，因为单独一个点值会让人高估精度。

## 5. 当前结果：三层指标，各自的结论不同

> ⚠️ **§5.1–§5.9 里的类别 Top-1（85.7% / 82.4%）都来自 n≤34 的小样本，不能引用。**
> 已用全量 544 条复测，结果是 **69.6%**，见 §5.10。
> 覆盖率类数字不受影响——它们的分母本来就是 544，不是"答对的那几条"。

完整报告见 [`baseline-20261110.md`](baseline-20261110.md)。

### 5.1 端到端（544 条分层抽样）

| 指标 | 值 | 判读 |
|---|---|---|
| 门控准确率 | 83.6%（95% CI 80.3–86.5） | 但多数类基线就有 82.9% |
| 门控特异度 | **4.3%** | 规则闸门**不成立**，只比基线高 +0.7pp |
| 类别 Top-1 | 0%（n=5） | 无解释力——被覆盖率卡住 |
| 覆盖率 | **1.7%** | 槽位抽取是瓶颈 |

### 5.2 检索层隔离实验（绕过抽取，451 条）

端到端覆盖率太低，判定能力测不出来。于是把抽取层摘掉，直接拿官方文本检索目录：

| 指标 | 值 |
|---|---|
| **Top-1** | **62.3%**（95% CI 57.7–66.7） |
| **Top-3** | **98.9%** |
| Macro-F1 | 0.599 |
| 多数类基线（全判 Ⅱ 类） | 45.2% |
| 随机猜（3 类） | 33.3% |

分类别：Ⅰ 类 F1 0.672、Ⅱ 类 F1 0.671、**Ⅲ 类 F1 0.455（召回仅 36.8%）**。

**这是目前唯一有解释力的效果数字**：比多数类基线高 17.1pp，
Top-3 98.9% 说明正确类别几乎总在前三里。

但 Ⅲ 类召回只有 36.8% —— 而 Ⅲ 类恰恰是风险最高的一类。**漏判 Ⅲ 类是这套系统最贵的错误**，
因为 Ⅲ 类和 Ⅱ 类的注册路径完全不同（国家局审评 vs 省级）。这是下一步最该优化的地方。

### 5.3 三条结论

**结论一：目录已经不是瓶颈了。** 1,689 个可定类节点、零校验问题、Top-3 98.9%。

**结论二：抽取层是瓶颈。** 544 条里 531 条在槽位抽取阶段就转成追问。
官方描述是「由…组成，用于…」的写法，很少直接写接触类型与有源/无源。
这把「必须接 LLM 抽取器」从一句待办变成了 `1.7%` 这个数字。

**结论三：规则闸门不成立。** 特异度 4.3%，96% 的「不作为医疗器械」会被漏判。
同一款「生理氯化钠溶液」，官方界定为不作为医疗器械，描述里却明写
「用作雾化治疗中的吸入剂」——关键词在这种样本上必然失效。

### 一条必须写明的限制

5.2 的数字是**词汇覆盖**的度量，不是语义理解能力的度量。
分类目录的「品名举例」就在检索语料里，而界定结果的产品名与它有大量共享词汇。
这不是数据泄漏（界定文本从不进目录），但它确实让词法检索占了便宜。
换成向量检索时**必须重跑这一组**，否则会误以为升级带来了提升。

### 5.4 Ⅲ 类召回：一次诊断、一个被证伪的假设、一个可交付的策略

#### 诊断：不是找不到，是选错了

| 正确类别的名次 | 占比 |
|---|---|
| 第 1 名 | 62.3% |
| 第 2 名 | 16.9% |
| 第 3 名 | 6.9% |
| 未进前 20 | 1.1% |

Top-3 已达 98.9%，说明**类别几乎总在候选里，问题出在最终取舍**。

误判高度集中：**子目录 22（临床检验 / IVD）占 76/170 = 45%**。

#### 假设一：扁平检索忽略了目录层级 → **证伪**

我原以为"先定子目录、再在子目录内定类别"会更好（这也符合注册专员的实际思路）。
实测相反：

| 策略 | Top-1 | Ⅲ 召回 |
|---|---|---|
| 扁平 top1 | 62.3% | 36.8% |
| 先定子目录 | **61.9%** | **32.8%** |

真因更朴素：Ⅲ 类与 Ⅱ 类的区分常常依赖**临床用途的风险属性**，
而同为 IVD 试剂的两条文本在词面上几乎一样。**纯词法检索在这上面有天花板，
换决策策略造不出信号。** 要突破得靠向量检索或额外的领域特征。

#### 交付：把风险偏好显式化，而不是埋一个阈值

`mc_domain/decision.py`。核心认识是：**选 Ⅱ 类还是 Ⅲ 类不是技术问题，是风险偏好问题。**

- Ⅱ 类走省级注册、Ⅲ 类走国家局审评 —— 判低了，企业走完整条错流程再被打回；
- Ⅲ 类多为植入/生命支持类 —— 判低了，是把高风险产品当低风险放过去。

所以"取最高分"并非天然正确，它只是**不偏向任何一类**。实测四种预设（451 条）：

| 预设 | α | Top-1 | Ⅰ召回 | Ⅱ召回 | Ⅲ召回 | Macro-F1 | 成本/百例 |
|---|---|---|---|---|---|---|---|
| strict | 0.00 | 62.3% | 73.8% | 71.1% | 36.8% | 0.599 | 88.7 |
| **balanced（默认）** | **0.05** | **62.1%** | 67.2% | 72.1% | **40.8%** | **0.602** | **84.0** |
| risk_averse | 0.10 | 61.2% | 61.5% | 68.6% | 48.8% | 0.601 | 79.2 |
| max_recall_iii | 0.20 | 57.9% | 53.3% | 60.8% | 57.6% | 0.579 | 74.5 |

成本口径：判低 = 3，判高 = 1，判对 = 0。

**为什么默认 balanced 不是妥协**：它的 Macro-F1（0.602）比 strict（0.599）**略高**，
成本低 5.3%，只有 Top-1 降 0.2pp。这是帕累托改进，不是取舍。

**为什么这比"调参"值钱**：
1. 取舍依据写进了代码（《医疗器械分类规则》多类别择高原则），不是一串魔法数字；
2. 用户能选——只做初筛再全量复核的场景用 `max_recall_iii` 才合理；
3. 结果里回传 `risk_preference`，**同一个问题换策略得到不同类别时，能解释为什么**。

#### 还没解决的部分

α 只能挪动取舍，不能提升信号。Ⅲ 类召回的上限由检索质量决定：
**要真正提高，需要向量检索 + 领域特征（如"是否用于伴随诊断/肿瘤分型"）。**
这条已经写进下一步，不是"再调调 α"。

### 5.5 LLM 槽位抽取：覆盖率 1.7% → 30.2%

把 `MC_NORMALIZER=llm`（qwen-plus）接上后：

| 抽取器 | 覆盖率 | 类别 Top-1 | 调用 / token |
|---|---|---|---|
| 关键词基线 | 1.7% | 0%（n=5） | 0 |
| **LLM（qwen-plus）** | **45.3%** | **85.7%（n=21）** | 53 次 / 28,558 |

**成本可以忽略**：平均 540 token/条，全量 544 条约 29 万 token。

但覆盖率只到 45.3%，剩下 54.7% 仍在槽位阶段转成追问（29 条）。
这不是接得不对，而是**官方描述本来就很少写接触类型与有源/无源**——
「由 XX 组成，用于 YY」这种写法里常常没有这两个维度。

所以下一步有两条路，需要产品判断而非技术判断：

1. **放宽槽位硬要求**：把 `contact_type` / `energy_type` 从"必需"降为"可选"，
   缺省时按目录条目反推，并在结论里标注"该项未确认"；
2. **维持现状**：把追问当成正确行为——注册专员本来就该补充信息。

倾向 (1)，但要保证降级路径**可见**（写进依据链），不能悄悄猜。

#### 一个真实调用才暴露的 bug

提示词明确要求"用户没说的一律返回 null"，于是模型对 `models` / `materials`
返回 `null`；而 `ProductProfile` 里这两个字段是 `list[str]`，直接
`model_validate` 会抛 **第一条样本就失败**。

正确语义：**标量字段的 null = 未抽取；列表字段的 null = 没有条目**，
后者应归一成 `[]`。已修并补了针对性测试。

#### 待查

53 条里有 8 条 `no_match`（17%）。真实目录有 22 个子目录，理论上不该这么高。
怀疑是短文本在 `coarse` 阶段的 bigram 召回不足，需要在 `coarse` 加兜底
（如命中为空时退回全目录检索）。

### 5.7 那 8 条 no_match：一个根因，27 倍提升

上一节留的待查项，查清楚了。全部 8 条的最后一个 step 都是 `coarse`——
**粗筛阶段一条子目录都没召回**。

#### 根因：子目录的检索文本只有 8 个字

分类目录里子目录节点本身没有产品描述，只有名字：

```
code=22  name=临床检验器械  definition=None  examples=[]
→ search_blob = "临床检验器械"
```

而查询是「基因测序用测序试剂盒（可逆末端终止测序法）」。
两者的字符 bigram：

| 查询 bigram | 目录名 bigram |
|---|---|
| 基因/因测/测序/序用/用测/测序/序试/试剂/剂盒 | 临床/床检/检验/验器/器械 |

**交集为空**。于是粗筛召回 0 条 → 直接 `no_match`，后面所有阶段都没机会跑。

这不是偶发：8 条里 6 条是 IVD 类（基因测序试剂、染色液、病理前处理试剂），
正是"产品名很具体、但生命周期归属在临床检验器械这个大类下"的典型。

#### 修法：容器节点的检索文本聚合子树

```python
tree.search_corpus(aggregate_containers=True)
```

子目录/一级类别的文本 = 自己的名字 + 全部子孙的名字 + 每个子孙的前 3 个品名举例
（截断到 2000 字符）。这样「22 临床检验器械」的文本里就带上了「基因测序」「试剂盒」，
粗筛能命中，后续阶段才有机会做正事。

**只改容器节点**，叶子节点的文本保持原样——否则会污染排序。这一点有专门的测试守住。
线上（`mc_medireg.catalog`）与评测脚本用的是同一个开关，避免"评测修好了线上没修"。

#### 效果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `no_match` | 8 / 53 | **0 / 53** |
| 覆盖率 | 30.2% | **45.3%** |
| 类别 Top-1 | 61.5%（n=13） | **85.7%（n=21）** |
| Macro-F1 | 0.617 | **0.839** |
| Ⅰ / Ⅱ / Ⅲ F1 | — | 0.947 / 0.769 / 0.800 |

准确率的连带提升不是巧合：那 8 条里金标是 Ⅰ 类和 Ⅲ 类，
召回修好之后它们本来就该被判对。

#### 为什么值得单独记一笔

这是典型的**检索前置阶段的静默失败**：没有异常、没有 5xx，
只是"没匹配到"——`no_match` 看起来像一个正常结果，很容易被当成"这个产品目录里没有"
而放过。定位靠的是把 `last_eval.json` 里每条失败样本的 `steps` 打出来，
看最后一个阶段停在哪。**没有那层 step 留痕，这条根因是查不出来的。**

### 5.8 覆盖率从 45.3% 到 77.4%：一次被证伪的推荐

上一节之后我判断"剩下 54.7% 卡在槽位"，建议把 `contact_type` / `energy_type`
从阻断性降为标注性。**做了之后覆盖率几乎没动**：

| 阶段 | 覆盖率 | 类别 Top-1 | needs_more_info | no_match |
|---|---|---|---|---|
| 关键词抽取 + 合成目录 | 1.7% | 0%（n=5） | 29 | 8 |
| + LLM 抽取 | 30.2% | 61.5%（n=13） | 29 | 8 |
| + **粗筛聚合修复** | **45.3%** | 85.7%（n=21） | 29 | **0** |
| + **槽位降级** | 43.4% | 85.0%（n=20） | 30 | 0 |
| + **类别感知歧义** | **77.4%** | 82.4%（n=34） | **12** | 0 |

（n=53，qwen-plus，其余条件相同。）

槽位降级这一行覆盖率甚至略降——因为 LLM 抽取本身有轻微波动，一个样本跨了阈值。
**结论：槽位不是瓶颈。** 我上一轮的推荐判断错了。

#### 真正的瓶颈：歧义判定把"同类别"也当成了歧义

`_is_ambiguous` 原来的逻辑只看分数差：

```python
return (top.score - second.score) / top.score < AMBIGUITY_MARGIN
```

于是「07-01-01 眼科超声诊断设备（Ⅱ类）」与「07-01-02 腹部超声诊断设备（Ⅱ类）」
分数接近时也会转成追问——**但这两个候选的管理类别相同，注册路径完全一样**，
追问一个对结论毫无影响的问题，只是在惩罚用户。

注册专员要的是**路径**（一类备案 / 二类省级 / 三类国家局），不是编码本身。
所以歧义应该定义在**结论层**，而不是编码层：

```python
if top.management_class == second.management_class:
    return False   # 同类别：编码再接近也不影响结论
return (top.score - second.score) / top.score < AMBIGUITY_MARGIN
```

一句话：**只有在管理类别真的分歧时才追问。**

#### 代价：准确率小幅下降是预期的

Top-1 从 85.7% 降到 82.4%，Macro-F1 0.839 → 0.813。
这不是退步——分母从 21 条扩大到 34 条，**新纳进来的是原先被拒答的难例**。
只用"答对的比例"比较两个覆盖率不同的系统是不公平的，必须同时报覆盖率。

#### 槽位降级仍然值得保留

虽然它没提升覆盖率，但它解决了一个真实的产品问题：
产品名称明明够检索用，却因为"接触类型未知"被拦在门外。
现在的行为是**给结论 + 标注未确认维度 + 保留追问入口**：

```json
{
  "status": "classified",
  "outcome": "II",
  "unconfirmed": ["contact_type", "energy_type"],
  "missing_slots": [{"slot": "contact_type", "question": "使用时会接触人体吗？…"}],
  "caveats": ["未确认的判定维度：接触类型、有源/无源。…补全后可能落到相邻类别，建议复判。"]
}
```

**关键在于"可见"**：降级不能悄悄发生，否则用户会以为结论建立在完整信息上。

### 5.9 向量检索：Ⅲ 类升上去了，Ⅰ 类塌了

词法检索在 Ⅲ 类召回上撞了天花板，所以接 `text-embedding-v4` 做向量检索，
并试了三路对照（451 条样本）：

**α=0（严格按最高分）**

| 检索方式 | Top-1 | Top-3 | Ⅰ召回 | Ⅱ召回 | Ⅲ召回 | Macro-F1 |
|---|---|---|---|---|---|---|
| **词法（字符 bigram）** | **62.5%** | 98.4% | 74.6% | 70.6% | 37.6% | **0.603** |
| 向量（text-embedding-v4） | 57.9% | 98.0% | **31.1%** | 78.4% | **50.4%** | 0.543 |
| 融合 词法=0.7 | 60.5% | 97.8% | 55.7% | 76.0% | 40.0% | 0.583 |

**α=0.05（均衡）**

| 检索方式 | Top-1 | Ⅰ召回 | Ⅲ召回 | Macro-F1 |
|---|---|---|---|---|
| 词法 | **61.6%** | 67.2% | 39.2% | **0.596** |
| 向量 | 55.9% | 19.7% | **73.6%** | 0.508 |
| 融合 词法=0.7 | 59.2% | 44.3% | 45.6% | 0.568 |

#### 结论：向量只买了 Ⅲ 类召回，代价是 Ⅰ 类崩塌

- Ⅲ 类召回确实上去了（37.6% → 50.4%，配 α=0.05 可达 73.6%），**证明词法天花板是真的**；
- 但 Ⅰ 类召回从 74.6% 掉到 31.1%，**Top-1 与 Macro-F1 全面低于词法**；
- 融合只能取中间值，没有出现"两者兼得"的点。

**没有任何一种配置在综合指标上超过词法。**

#### 三次负结果指向同一个原因

| 尝试 | 结果 | Ⅲ 类 | Ⅰ 类 |
|---|---|---|---|
| 先定子目录（层级） | Top-1 61.9% | 32.8% | — |
| 重排序 qwen3-rerank | Top-1 64.4% | 52.0% | 45.8% |
| 向量 text-embedding-v4 | Top-1 57.9% | 50.4% | 31.1% |

三种彼此独立的方法（层级约束、交叉编码器、稠密向量）**都把结论往高类别推，
并且都牺牲 Ⅰ 类**。这不是实现问题，而是：

> **管理类别不是文本相似度的函数。**

Ⅰ 类多是低风险的敷料、护理、手动器械，词面上"医疗器械感"弱；
Ⅲ 类是植入/生命支持，描述更"危急"。任何语义相似度模型都会学到这个语感偏差，
于是把产品往 Ⅲ 类推。而真正的 Ⅲ 类判定依据（是否用于伴随诊断、是否植入、
是否生命支持）**在文本里经常根本不出现**。

#### 那什么值得做

方向不是更好的检索，而是**换任务形式**：

1. **有监督分类**。官方界定结果已有 1,244 条类别范围内样本，可以直接训
   TF-IDF + 逻辑回归的基线——它学的是"哪些词与哪个类别相关"，而不是"哪条最像"，
   目标函数终于对齐了。免费、离线、当天可跑。
2. **补领域特征**。把"是否用于伴随诊断 / 是否植入 / 是否生命支持"这类
   分类规则维度抽成显式特征——这正是 `contact_type` / `energy_type` 本该扮演的角色，
   现在它们只是标注字段，没有进入判定。
3. α 旋钮仍然是当下最划算的 Ⅲ 类召回手段（免费、确定性、可解释）。

#### 产物与成本

- 索引落盘在 `data/raw/catalog_vector_index/`（1,917 × 1,024，7.8 MB），评测不重复计费；
- 建索引：192 次请求 / **21.9 万 token**；
- 查询预热：451 条一批算完，46 次请求 / 5 万 token。

### 5.6 重排序：一个负结果，和一个额度问题

端到端诊断提示 Top-3 98.9% / Top-1 62.3%，看起来正是重排序的用武之地。实测相反。

**排序质量对照（α=0，只看排序，n=90）**

| 路径 | Top-1 | Ⅰ召回 | Ⅲ召回 |
|---|---|---|---|
| 单段（字符 bigram） | **68.9%** | 79.2% | 56.0% |
| 纯重排 compact | 64.4% | 45.8% | 52.0% |
| 纯重排 full | 63.3% | 41.7% | 68.0% |

- **Top-3 不动（96.7%）**——重排序不改变召回，符合预期；
- **Top-1 变差**，且 Ⅰ 类召回塌陷、Ⅲ 类上升 —— 它做的是**类别偏置**。

原因：重排序优化的是**语义相关度**，而我们的目标是**监管类别**。
类别是命中条目的属性，不是文本相似度的函数——两者不是同一个目标函数。
而"往高类别偏"这件事，`risk_averse` / `max_recall_iii` 已经能确定性做到，**且不花钱**。

**结论：P1 默认不启用重排序。** 客户端保留（`mc_domain/rerank.py`），
因为 P2 的标签审核里目标是"条款 vs 标签项"匹配，与语义相关度是对齐的。

#### 额度：`qwen3-rerank` 免费额度已耗尽

继续跑对照时报 `AllocationQuota.FreeTierOnly`（HTTP 403）。
需要在百炼控制台**充值或关闭"仅使用免费额度"**才能继续。
同一账户的 `qwen-plus` / `qwen-max` 正常，所以抽取不受影响。

> 顺带修了一个环境 bug：这台机器的 `NO_PROXY` 含 `[::1]`，
> 会让 `httpx.Client()` **在构造阶段**就抛 InvalidURL。改成显式传代理、
> 忽略 NO_PROXY（见 `mc_domain/env.py::http_client_kwargs`）。

### 5.10 全量复测：把小样本上的 Top-1 修正掉

前面几轮为了控制成本，类别指标都只在 n=13~34 的小样本上算。
本次跑全量 544 条（qwen-plus 抽取 / 真实目录 / 288,164 token）：

| 指标 | 值 |
|---|---|
| 覆盖率 | **77.4%**（421 条给出结论，123 条转追问，0 条无匹配） |
| **类别 Top-1** | **69.6%**（95% CI **64.6–74.1**，n=355） |
| 类别 Top-3 | 85.1% |
| Macro-F1 | **0.669** |
| Ⅰ 类 | P 72.7% / R 74.2% / F1 0.735（支持度 97） |
| Ⅱ 类 | P 69.4% / R 81.7% / F1 0.751（支持度 164） |
| **Ⅲ 类** | P 65.1% / R **43.6%** / F1 0.522（支持度 94） |
| 门控 | 准确率 83.6%（CI 80.3–86.5）/ 特异度 **4.3%** |

#### 修正了什么

| | 小样本（n=34） | 全量（n=355） |
|---|---|---|
| Top-1 | 82.4% | **69.6%** |
| Macro-F1 | 0.813 | **0.669** |

**小样本的数字不是"错的"，是"不能引用的"**：n=34 时 82.4% 的 95% 区间约 66%–92%，
把 69.6% 也包在里面。也就是说那个 82.4% 从一开始就没有分辨力。

值得单独记一条：**覆盖率的分母是 544，稳定；Top-1 的分母是"答出结论的那几条"，
样本一小就飘。** 以后报类别指标，必须同时报 n 和区间，否则等于没报。

#### 结论没变，但更硬了

- Ⅲ 类召回 **43.6%**，与检索层隔离实验（37.6%）方向一致，确认是结构性短板而非噪声；
- 门控特异度 **4.3%**，与 n=544 的门控评测完全吻合——那个数字本来就是稳的。

## 7. 这套方法里，哪些是会带进面试的

1. **"我没有评测集"通常意味着"我没找官方标注"** —— 6434 条官方裁决摆在那。
2. **主动检查 train/test 泄漏**（品名举例 vs 检索索引），而不是等着被抓。
3. **主动报多数类基线**，承认自己的指标比基线只高 0.7pp。
4. **把拒答单列**，不混进准确率。
5. **量化自己的失败**：覆盖率 1.5%、特异度 4.3% —— 这两个数字比任何"效果良好"都有信息量。
