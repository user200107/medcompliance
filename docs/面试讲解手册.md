# 面试讲解手册

> 目标：让你在 **20 分钟内**能把这套东西讲清楚，并且扛得住追问。
> 每个应用只要求你记住三件事：**它解决什么、我做了什么取舍、数字是多少**。

---

## 0. 一句话版本（电梯陈述，30 秒）

> 我在医疗器械这个强监管行业里，用一套法规底座做了三个面向不同岗位的 AI 应用——
> 注册专员查分类、QA 查标签、RA 顾问查卷宗。
> 三个应用共享同一个法规知识底座，但各自的核心难点完全不同。
> 我的统一主张是：**模型只负责翻译，判定交给确定性引擎，AI 出的所有结论都要人确认才能对外**。

这套话能撑住 5 分钟。往下每一节是对应的细节。

---

## 1. 套件整体：为什么是一个仓库

**一句话**：一个行业、一套底座、三个独立部署的应用。

**结构事实**（可以直接说）：

| 层 | 内容 |
|---|---|
| `mc-domain` | 共享底座：分类目录树、法规版本时效、产品主数据、评测机 |
| `mc-medireg` | P1 注册路径问答（:8011） |
| `mc-labelguard` | P2 标签合规审核（:8012） |
| `mc-dossier` | P3 卷宗一致性审查（:8013） |

**必然被问：为什么不做成三个仓库？**

> 因为单领域方案的全部价值在于底座被复用。拆三个仓库会立刻陷入两难：
> 要么把底座复制三遍（那"共享"是假的），要么发私有包并维护版本对齐——
> 我一个人业余做这个纯属损耗。
> 现在这套结构同时满足两个目标：**部署上是三件事**（三个镜像、三个端口、可单独启动），
> **维护上是一个项目**（共享库本地解析，改一个实体只提一个 PR）。

**必然被问：那怎么证明这不是一个产品拆成三个？**

三点，都能用代码验证：

1. **不同岗位、不同权限**：注册专员 / QA / RA 顾问在真实器械公司是三个部门；
2. **不同输入模态、不同失败模式**：
   - P1 失败是**答错**（引用了已废止的指导原则）
   - P2 失败是**漏看**（标签少了 UDI 没发现）
   - P3 失败是**对不上**（技术要求写 Ø3.20、检验报告写 Ø3.50 没发现）
3. **共享的是库，不是应用**：P2/P3 各自能单独 build、单独起、单独评测。

## 2. P1 MediReg：注册路径知识引擎

### 2.1 它解决什么

给注册专员用：输入产品描述，输出**管理类别**（一类/二类/三类）、分类编码、适用的指导原则。

### 2.2 三个设计取舍（重点讲这个）

**取舍一：模型只做翻译，判定交给确定性引擎。**

> LLM 只负责把口语翻译成结构化槽位（接触类型 / 有无源 / 预期用途）。
> "这是几类"永远由规则阶段给出。
> 因为一旦让模型直接输出分类编码，就同时失去**可复现性**和**可解释性**——
> 而这两样正是注册专员愿意为工具付费的全部理由。

**取舍二：法规版本时效——`status` 描述的是"现在"，不是"as_of 那时"。**

> 一个现在标为 `SUPERSEDED` 的法规版本，在 2019–2023 那个窗口里就是当时的现行版。
> 如果按 `status == CURRENT` 过滤，`version_at("2020-01-01")` 会返回 `None`，
> 「按提问时点检索法规」这个功能整个失效——而那恰恰是 P1 存在的理由。
> 所以判定只认日期窗口，`status` 仅用于排除征求意见稿。
> **这个 bug 是我写完 smoke test 才发现的，单测不写永远发现不了。**

**取舍三：风险偏好显式化，而不是埋一个阈值。**

> 判低和判高的代价不对称：Ⅱ 类走省级注册、Ⅲ 类走国家局审评，判低了企业走完整条错流程再被打回；
> Ⅲ 类多为植入/生命支持，判低了是把高风险当低风险放过去。
> 所以"取最高分"并非天然正确，它只是**不偏向任何一类**。
> 我把它做成 4 档可配置策略，取舍依据写进代码（《医疗器械分类规则》多类别择高原则），
> 策略名随结果回传，**同一个问题换策略得到不同类别时能解释为什么**。

### 2.3 数字（背这几个）

| 项 | 值 |
|---|---|
| 真实分类目录 | 1,703 条 → **1,917 节点**（1,689 可定类），树校验零问题 |
| 评测集 | **1,657 条**官方分类界定裁决（19 个公告批次，2019-02 → 2026-08） |
| 端到端覆盖率 | **77.4%**（n=53，qwen-plus 抽取） |
| 类别 Top-1 | **69.6%**（95% CI 64.6–74.1，n=355），Macro-F1 **0.669** |
| 检索层隔离实验 | Top-1 **62.3%**（多数类基线 45.2%），Top-3 **98.9%** |
| 门控特异度 | **4.3%** ← 承认它不可用 |
| 风险偏好 balanced | Top-1 62.1%，Ⅲ 类召回 40.8%，成本 84.0/百例（strict 是 62.3% / 36.8% / 88.7） |

### 2.4 三次负结果（这是最能加分的一段）

> 我为 Ⅲ 类召回做过三次尝试，**全部失败**，而且失败方式一致：

| 尝试 | Top-1 | Ⅲ 类召回 | Ⅰ 类召回 |
|---|---|---|---|
| 先定子目录（层级约束） | 61.9% | 32.8% | — |
| 重排序 qwen3-rerank | 64.4% | 52.0% | 45.8% |
| 向量 text-embedding-v4 | 57.9% | 50.4% | 31.1% |

> 三种彼此独立的方法——层级约束、交叉编码器、稠密向量——**都把结论往高类别推，都牺牲 Ⅰ 类**。
> 结论是：**管理类别不是文本相似度的函数。**
> Ⅰ 类多是敷料、护理、手动器械，词面上"医疗器械感"弱；Ⅲ 类是植入/生命支持，描述更"危急"。
> 任何语义相似度模型都会学到这个语感偏差。
> 而真正的 Ⅲ 类判据（是否用于伴随诊断、是否植入、是否生命支持）**在文本里经常根本不出现**。
>
> 所以下一步不是"换更好的检索"，而是**换任务形式**：用 1,244 条标签样本训有监督分类器，
> 让它学"哪些词与哪个类别相关"，而不是"哪条最像"——目标函数才对齐。

### 2.5 可能被追问

**Q：69.6% 的 Top-1 是怎么测的？**
> 1,657 条官方裁决里分层抽样，同一批样本跑完整流水线。抽样是按标签分层的，不是取前 N 条——
> 站内按时间排序，取前 N 条会得到一个"只有 2019 年"的偏样本。
> 全量 544 条复测，n=355，区间 64.6–74.1。小样本上的 82.4% 我已经从文档里删掉了——
> n=34 时区间宽到没有分辨力，那个数字从一开始就不该引用。

**Q：为什么不用分类目录的「品名举例」当评测输入？**
> 因为检索索引 `search_blob` 本身就包含 `examples`，拿它当输入等于测模型能不能背出索引内容，
> 准确率会漂亮到接近 100%，然后一被问"评测集和索引有重叠吗"就崩。
> 界定结果的「产品详情」是企业送审时写的原文，从不进任何目录，才是真 held-out。

**Q：覆盖率只有 77.4%，剩下 23% 呢？**
> 转成了追问（`needs_more_info`），主要是两个原因：跨类别的真歧义（该问），
> 以及官方描述里确实没写接触类型/有源无源。
> 我做过一次"放宽槽位硬要求"的改动，覆盖率几乎没动（45.3% → 43.4%），
> **说明槽位不是瓶颈**——真凶是歧义判定把"同类别不同编码"也当成了歧义。
> 改成只在**管理类别真的分歧**时才追问，覆盖率从 43.4% 跳到 77.4%。
> 这个自我更正我写进了文档。

**Q：门控特异度 4.3%，那这个闸门还有什么用？**
> 没用，我承认。规则只能拦下表述里明写「无治疗作用 / 不涉及疾病」的少数样本。
> 准确率 83% 看着不错，但多数类基线就有 82.9%——只高 0.7pp，等于没有信息。
> 这正是我把它量化的目的：**避免拿一个 83% 去吹**。要做对需要语义判定 + 人工复核。

## 3. P2 LabelGuard：标签合规审核

### 3.1 它解决什么

给 QA 用：送一张标签（文本或结构化字段），输出**逐项必标项检查表** + 每项条款依据 + 三态结论。

### 3.2 三个设计取舍

**取舍一：必标项是数据，不是代码。**

> 15 条规则写成一张表，加一个审查项 = 表里加一行 + 枚举加一个值，判定引擎不动。
> 每条判定自带法规条款（第 6 号令 / YY/T 0466.1 / UDI 规则）。
> 这是我理解的"法规条款驱动产品"的具体形态。

**取舍二：三态判定，低置信度只许「不可判定」。**

> 缺项 / 格式错 / 与主数据不符 → **违规**；
> 看不清 / 没抽到 → **不可判定**。
> 把"看不清"判成"违规"是冤枉企业，判成"合规"是放过风险。
> 这条有专门的测试钉住。

**取舍三：AI 只出草稿，审核员署名确认后才有不可变快照。**

> 这条把"AI 不能负最终责任"从一句免责声明变成了代码：
> 送审返回 `is_draft: true`；确认必须署名；基于旧 revision 的确认返回 409。
> 因为标签结论会被拿去整改、甚至作为合规证据。

### 3.3 数字

| 项 | 值 |
|---|---|
| 必标项规则 | **15 条** |
| 判定引擎（fields 模式） | P **100%** / R **100%** / F1 **1.000**，负控假阳性 **0%** |
| 整链路（text 模式） | P 100% / R **80%** / F1 0.889 |
| 两者差距 | **20pp** ← 就是文本抽取层的损失 |

### 3.4 两个真实 bug（都是测试逼出来的）

**bug 1：产品属性与符号存在被混成一个字段。**
> 原本 `sterile_mark` 一个字段同时表示"产品是无菌的"和"标了无菌符号"。
> 这会导致一个真实漏洞：**无菌产品漏标符号时，因为字段有值被判成"已标注"**。
> 拆成 `is_sterile`（属性，决定是否适用）+ `sterile_mark`（符号，被检查对象）后才有测试能抓到它。

**bug 2：非强制项缺失被判成违规。**
> 生产许可证、警示信息、说明书指引是非强制项，缺失时原逻辑判违规——
> 那是让企业去整改一个法规并不要求它标注的项。
> 这个 bug 会直接污染精确率，是在跑评测前被发现的。

### 3.5 可能被追问

**Q：100% 的检测率可信吗？**
> 不完全可信，我在文档里写明了：合成集的 ground truth 是**人为埋的**，
> 所以它衡量的是"引擎对已知缺陷类型的检出能力"，**不是真实标签的绝对准确率**。
> 真正有价值的不是 100%，而是 **fields 100% vs text 80% 那 20pp 差距**——
> 它精准定位了损失在抽取层，而不在判定层。

**Q：为什么 text 模式漏的都是"符号缺失"这类？**
> 因为在文本里「无菌」这个词既是产品属性也是符号存在，二者无法区分。
> **文本模式结构性地看不到符号是否存在**，只有视觉抽取才抓得到。
> 这 20pp 就是接 qwen-vl 的量化理由，而不是"感觉视觉更专业"。

**Q：视觉接了吗？**
> 没接，我在 README 和 `/healthz` 里都写着 `vision: not_implemented`。
> 但接口层留了 `fields` 入参——视觉模型只要产出同样的 `LabelExtraction`，
> 下游判定引擎一行不用改。这条边界是刻意设计的。

## 4. P3 DossierReview：卷宗一致性审查

### 4.1 它解决什么

给 RA 顾问用：送一套申报资料（技术要求 / 说明书 / 检验报告），输出**章节缺项** + **跨文档属性冲突**。

### 4.2 最核心的一句话

> **它解决的不是检索问题。**
> RAG 能回答"技术要求里写了什么"，但回答不了「技术要求写 Ø3.20、检验报告写 Ø3.50，谁对？」
> 那必须先把多份文档抽成结构化字段，再做对齐与比对。

### 4.3 三个设计取舍

**取舍一：归一化的目标是"吃掉写法差异、留下实质差异"。**

> 该吃掉：`Ø3.20 mm` vs `3.2mm`、`3年` vs `36个月`、`A-100` vs `a 100`
> 该留下：`Ø3.20` vs `Ø3.50`、`A-100` vs `A-101`
> **误报比漏报更能摧毁信任**：审核员连续三次被假冲突打扰，就不会再看报告了。

**取舍二：三态结论，第三态是"无法核对"。**

> 只有一份文档提到该属性时，既不能算一致（没比对），也不能算冲突。
> 把它悄悄算进"一致会让报告虚高"——这是这类工具最常见的自欺。

**取舍三：归一化不出可比值时，判"无法核对"，不退回原文比字符串。**

> 尺寸写成 `3.2` 没有单位，工具无权假定是 mm。
> 退回原文会把它和 `Ø3.20 mm` 判成冲突——那是制造假冲突。
> 所以这种情况整个属性降级为"无法核对"。

**取舍四（产品层）：P3 刻意做成无状态，没有发布门禁。**

> 这不是偷懒，是两个应用定位不同：
> P2 的结论会被拿去整改甚至作为合规证据 → 必须人署名确认、不可变快照；
> P3 的产出是待办清单 → 每次请求按当时文档重新算即可。
> **能讲清"为什么两个应用不该一样"，比给它们套同一套门禁更有说服力。**

### 4.4 数字

| 项 | 值 |
|---|---|
| 核对属性 | **6 类**（型号/尺寸/灭菌方式/有效期/生产地址/结构组成） |
| 合成卷宗情形 | **10 种**（6 真冲突 + 2 仅写法不同 + 1 缺章节 + 1 无缺陷） |
| 冲突检测 | P **100%** / R **100%** / F1 **1.000** |
| 负控假阳性 | **0 / 54**（只改写法不该报冲突） |
| 缺项召回 | **100%** |

### 4.5 可能被追问

**Q：又是 100%，这次为什么不能吹？**
> 因为判定是**确定性规则**，缺陷是**人为埋的**。这类任务的 100% 只说明归一化规则覆盖了
> 构造时考虑到的那几类写法差异。我在报告末尾写了这句话，没把它当亮点。
> 真正有信息量的是"负控 0 假阳性"——它证明归一化没有退化成"什么都报冲突"。

**Q：如果真实卷宗里有你没埋过的写法怎么办？**
> 会误报或漏报。我的缓解措施是三态设计：归一化不出可比值时判"无法核对"而不是冲突，
> 所以最坏情况是"少报"，不是"乱报"。要覆盖更多写法，需要从真实卷宗里回流样本，
> 那是产品化阶段的事，不是作品集该假装做到的事。

## 5. 三个应用为什么值得放在一起（套件叙事）

| | 输入 | 核心算法 | 输出 | 失败模式 |
|---|---|---|---|---|
| P1 | 长文档 / 厂商描述 | 目录树遍历 + 混合检索 + 时效路由 | 带引用结论 | 答错 |
| P2 | 标签图 / 文本 | 视觉抽取（待接）+ 必标项规则 | 逐项检查表 | 漏看 |
| P3 | 多份文档 | 结构化抽取 + 归一化 + 比对 | 冲突清单 | 对不上 |

**没有一行重复。** 而且三者共享同一条工程主张：**模型只翻译，判定交给确定性引擎，AI 结论要人确认**。

## 6. 我能承认的短板（主动说，别等人问）

1. **视觉抽取未接**。P2 的 text 模式漏检 20pp 就是这个缺口。
2. **门控不可用**。特异度 4.3%，规则拦不住"不作为医疗器械"。
3. **Ⅲ 类召回仍是短板**。37–40%，三次尝试都失败，原因已定位到"类别不是文本相似度的函数"。
4. **合成集的 100% 不等于真实准确率**。P2/P3 的指标只能衡量引擎的相对能力。
5. **前端只有一个页面**（规划中）。面试时我展示的是"产品档案"一屏，不是三个完整模块。
6. **没有 Alembic 迁移**。目录与产品尚未落库，现在是启动时载入 CSV。

**为什么主动说**：主动承认差距的人会被认为可靠；被问出来的人不会。

## 7. 演示脚本：点什么、别点什么

**先说清楚前提**：P1 的检索是**字符 bigram 基线**，产品名与目录「品名举例」字面接近时准，
差异大时会明显出错。以下是我在真实目录（1,917 节点）上实测的结果，**照着点，别自由发挥**。

### 会成功（可以主动点）

| 输入 | 输出 | 说明 |
|---|---|---|
| 超声切割止血刀……（有源/接触组织/无菌/一次性） | `01-01-03.1` 有源手术器械 → 超声手术设备附件 / **Ⅲ 类** | 子目录与类别都对 |
| 骨蜡……（植入体内/无源/无菌） | `14-08-01` 可吸收外科止血材料 / **Ⅲ 类** | 合理 |

### 会失败（别主动点）

| 输入 | 实际输出 | 问题 |
|---|---|---|
| 彩色多普勒超声诊断仪 | `14-01-03` 无针注射器 | **完全错** |
| 医用外科口罩 | `14-14-03` 隔离衣帽 | 类别对（Ⅰ 类）、编码错 |
| 便携式心电监护仪 | `16-02-05.2` 眼科器械 | 完全错，且转成了追问 |

### 如果面试官自己输入了别的东西（大概率）
