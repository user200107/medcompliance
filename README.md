# MedCompliance Suite · 医疗器械合规智能体套件

一个行业，一套底座，三个面向不同岗位的应用。

| | 应用 | 干什么 | 用户 | 状态 |
|---|---|---|---|---|
| **P1** | `mc-medireg` MediReg 械规通 | **问**：几类、走什么路径、要交哪些资料 | 注册专员 / 研发 | ✅ 分类判定 + 评测 |
| **P2** | `mc-labelguard` 标签哨兵 | **看**：这张标签/说明书能不能过 | QA / 质量部 | ✅ 必标项引擎 + 审核门禁 |
| **P3** | `mc-dossier` 卷宗审查 | **审**：这套申报资料缺什么、哪儿自相矛盾 | RA 顾问 | ✅ 一致性审查 |

三者共享 `mc-domain` 里的法规知识底座（分类目录树 + 法规版本时效 + 产品主数据）。
**共享的是库，不是应用**——三个服务各自独立部署、独立评测、可以单独交付。

| 应用 | 指标 | 值 |
|---|---|---|
| P1 | 真实目录 / 评测集 | 1,917 节点（1,689 可定类）/ 1,657 条官方裁决 |
| P1 | 类别 Top-1 | **82.4%**（Macro-F1 0.813，覆盖率 77.4%） |
| P2 | 必标项判定 | fields 模式 P/R **100%**；text 模式 R **80%**（差 20pp = 视觉层必要性） |
| P3 | 跨文档冲突 | P/R **100%**，负控假阳性 0/54 |

**171 个测试全绿。** 每个数字都有出处，见 [docs/evaluation/](docs/evaluation/README.md)；
面试怎么讲见 [docs/面试讲解手册.md](docs/面试讲解手册.md)。

**演示页**：`apps/web/index.html`，单文件、零构建，一屏串联三个应用
（分类结论 → 标签检查表 → 卷宗冲突）。启动：

```bash
python scripts/serve.py medireg     # :8011
python scripts/serve.py labelguard  # :8012
python scripts/serve.py dossier     # :8013
python scripts/serve_web.py         # :5180  ← 打开这个
```

> 前端刻意零构建：为一张演示页引 100MB `node_modules` 不划算，
> 而三个服务才是重点。产品化时换 Vue + nginx，接口层不用改。

## 1. 为什么是一个仓库

单领域方案的全部价值在于**底座被三个应用复用**。拆成三个仓库就会立刻陷入两难：
要么把底座复制三遍（那"共享"是假的），要么发私有包并维护版本对齐（一个人业余做这个纯属损耗）。

换成这套结构，两个目标同时成立：

- **部署上是三件事**：三个独立镜像、三个端口、三个端口各自可单独 `docker compose --profile` 启动
- **维护上是一个项目**：共享库本地 workspace 解析，改一个实体名只提一个 PR

# 看分类判定的完整依据链

# 起服务（脚本会处理 monorepo 的路径，不用记 PYTHONPATH）

python scripts/serve.py labelguard  # P2 → :8012
python scripts/serve.py dossier     # P3 → :8013

> ⚠️ 别直接用 `uvicorn mc_medireg.main:app --app-dir packages/mc-medireg/src`：
> uvicorn 的 `--app-dir` 只能加一个路径，而 `mc_medireg` 依赖兄弟目录的 `mc_domain`，

所以**不用先 `pip install -e` 就能跑**。业余项目里这层摩擦会直接导致"懒得跑测试"。

## 4. 三条设计主张

这三条贯穿全部代码，也是面试时唯一需要讲清楚的东西。

### 4.1 模型只做翻译，判定交给确定性引擎

LLM 只负责把口语翻译成结构化槽位（接触类型 / 有无源 / 是否无菌）。
"这是几类"永远由 `mc_domain.classify` 的规则阶段给出。

一旦让模型直接输出分类编码，就同时失去**可复现性**和**可解释性**——
而这两样正是注册专员愿意为工具付费的全部理由。

### 4.2 失败必须抛异常，绝不降级成空结果

`NormalizationFailed` 存在的原因，是上一代项目踩过的坑：
视觉模型解析失败返回 `{}`，随后 `setdefault("confidence", 0.5)` 把它包装成
"成功但为空"的结果，直接流进下游判定。**等价于把"模型挂了"变成了"专业结论"。**

这里的规矩：解析失败 → `NormalizationFailed` → HTTP 502；
字段合法但用户确实没说 → 保持 `None` → 生成追问。
**这两种情况必须走不同的路。**

### 4.3 依据链和结论一起交付

每个结论都带 `steps`（判定路径）+ `evidence`（目录条目原文）+ `rejected`（被排除的候选及原因）。

「为什么不是它」和「为什么是它」一样是交付物——
注册专员推翻结论时，需要看到系统原本考虑过哪些类别、因为什么放弃。

## 5. 评测：没有人工标注预算时怎么办

**结论：器械这个领域不需要自己标注。** 官方已经把答案标好了。

[医疗器械分类界定结果汇总](https://app.nidc.org.cn/biaogzx/dataGk.do?formAction=listFljdResult)
（中国食品药品检定研究院公开查询，共 6,434 条）里，一条记录就是一条 `(输入, 标签)`：

| 字段 | 作用 |
|---|---|
| 产品名称 + 产品详情 | 输入（企业自己写的组成与预期用途） |
| 产品类别 | 标签（官方裁决） |

本次抓取 **1,657 条**，覆盖 19 个公告批次、2019-02 → 2026-08。

**为什么不用分类目录的「品名举例」**（成本更低的那条路）：
检索索引 `search_blob` 本身就包含 `examples`，拿它当评测输入等于**测能不能背出索引内容**。
界定结果的「产品详情」从不进任何目录，是真 held-out。

**分类目录也是抓的**：同一个站的[分类目录库](https://app.nidc.org.cn/biaogzx/dataGk.do?formAction=listFlmlk)
（1,703 条）有子目录/一级/二级、产品描述、预期用途、品名举例、管理类别。
`scripts/crawl_catalog.py` 转成 **1,917 个节点**（1,689 个可定类），树校验零问题。
不用去下载官方 Word/PDF 附件——那是给自己找麻烦。

### 端到端（544 条分层抽样）

| 指标 | 值 | 判读 |
|---|---|---|
| 门控准确率 | 83.6%（95% CI 80.3–86.5） | 但多数类基线就有 82.9% |
| 门控特异度 | **4.3%** | 规则闸门**不成立**，只比基线高 +0.7pp |
| 类别 Top-1 | 0%（n=5） | 无解释力——被覆盖率卡住 |
| 覆盖率（关键词抽取） | 1.7% | 槽位抽取是瓶颈 |
| **覆盖率（qwen-plus 抽取）** | **77.4%** | 接上 LLM + 两处修复后 45 倍；约 540 token/条 |

### 检索层隔离实验（绕过抽取，451 条）

覆盖率太低，判定能力测不出来，所以把抽取层摘掉，直接拿官方文本检索目录：

| 指标 | 值 |
|---|---|
| **Top-1** | **62.3%**（95% CI 57.7–66.7） |
| **Top-3** | **98.9%** |
| 多数类基线（全判 Ⅱ 类） | 45.2% |
| 随机猜 | 33.3% |

**这是目前唯一有解释力的效果数字**：比基线高 17.1pp，Top-3 98.9%。

### 重排序：一个负结果

端到端诊断提示 Top-3 98.9% / Top-1 62.3%，看起来正等着重排序。实测相反：

| 路径 | Top-1 | Ⅰ召回 | Ⅲ召回 |
|---|---|---|---|
| 单段 | **68.9%** | 79.2% | 56.0% |
| 纯重排 | 64.4% | 45.8% | 52.0% |
| 纯重排 full | 63.3% | 41.7% | 68.0% |

**重排序优化的是语义相关度，而目标是监管类别——不是同一个目标函数。**
它的实际效果是类别偏置，而这件事 `α` 旋钮免费就能做。所以 P1 **默认不启用重排序**，
客户端保留给 P2（标签审核里两者目标是对齐的）。

> 同理，`text-embedding-v4` 的向量检索也没有超过词法：Ⅲ 类召回 37.6% → 50.4%，
> 但 Ⅰ 类从 74.6% 塌到 31.1%，Top-1 与 Macro-F1 全面更低。
> **三次独立尝试（层级约束 / 重排序 / 稠密向量）都以牺牲 Ⅰ 类为代价抬高 Ⅲ 类**——
> 说明管理类别不是文本相似度的函数，问题不在检索质量。详见 5.9。

### Ⅲ 类召回：诊断出来的真问题

Ⅲ 类召回只有 36.8%，而它是最贵的一类错误——Ⅱ 类走省级注册、Ⅲ 类走国家局审评，
判低不是"稍微不准"，是"完全走错流程"。

诊断先给出一个反直觉的事实：**Top-3 98.9% 而 Top-1 只有 62.3%**，
正确类别几乎总在候选里，问题在最终取舍。误判的 45% 集中在子目录 22（IVD）。

我试过一个"更聪明"的假设——先定子目录再定类别——**被证伪了**（61.9% / Ⅲ 召回 32.8%，
比扁平还差）。真因是：Ⅲ 与 Ⅱ 的区分依赖临床用途的风险属性，
同为 IVD 试剂的两条文本词面几乎一样。词法检索有天花板，换策略造不出信号。

所以可交付的做法是把**风险偏好显式化**（`mc_domain/decision.py`）：

| 预设 | α | Top-1 | Ⅲ召回 | Macro-F1 | 成本/百例 |
|---|---|---|---|---|---|
| strict | 0.00 | 62.3% | 36.8% | 0.599 | 88.7 |
| **balanced（默认）** | 0.05 | 62.1% | **40.8%** | **0.602** | **84.0** |
| risk_averse | 0.10 | 61.2% | 48.8% | 0.601 | 79.2 |
| max_recall_iii | 0.20 | 57.9% | 57.6% | 0.579 | 74.5 |

成本口径：判低 3 / 判高 1 / 判对 0。

`balanced` **不是妥协而是帕累托改进**：Macro-F1 比 strict 略高、成本低 5.3%，
只牺牲 0.2pp 的 Top-1。取舍依据写进代码（多类别择高原则），
策略名随结果回传，同一个问题换策略得到不同类别时能解释为什么。

### 三条结论

1. **目录不再是瓶颈**：1,689 个可定类节点、零校验问题、Top-3 98.9%。
2. **抽取层是瓶颈，但已接上并排掉两个坑**：关键词抽取覆盖率 1.7% → qwen-plus **77.4%**
   （n=53，no_match 归零，类别 Top-1 **82.4%**，Macro-F1 0.813）。
   两个坑是：粗筛把子目录的检索文本做成了 8 个字（`no_match` 全部来自这里）；
   歧义判定只看分数差、把"同类别不同编码"也变成追问（`needs_more_info` 从 30 降到 12）。
3. **规则闸门不成立**：特异度 4.3%，96% 的「不作为医疗器械」会被漏判。
   同一款「生理氯化钠溶液」，官方界定为不作为医疗器械，描述里却明写
   「用作雾化治疗中的吸入剂」——关键词在这种样本上必然失效。

> 限制：5.2 的数字是**词汇覆盖**的度量，不是语义理解的度量。
> 检索语料里含目录的「品名举例」，与界定结果的产品名有大量共享词汇。
> 这不是数据泄漏（界定文本从不进目录），但换向量检索时**必须重跑这一组**，
> 否则会误以为升级带来了提升。

完整方法、合规边界与复现命令见 **[docs/evaluation/README.md](docs/evaluation/README.md)**。

### 这台评测机本身的三个克制

- **报多数类基线**，并承认自己只高 0.7pp
- **拒答单列**，不混进准确率（否则"覆盖不足"和"判错"会混成一个数字）
- **标签空间比系统输出空间大**（官方 7 种结论 vs 系统 4 种），
  表达不了的 9.5% 显式排除并计数，不塞进某一类凑数

> 合规：原始数据只本地使用、不再分发，`data/raw/` 已忽略。
> 仓库里只留指纹（记录数 / SHA-256 / 时间范围）作为"确实跑过"的凭据。

## 6. 编写过程中被测试逼出来的 bug

| # | 症状 | 根因 | 为什么危险 |
|---|---|---|---|
| 1 | 目录树所有非根节点 `level=0` | 层级推导少加 1 | 树校验必挂，只有导入真目录才暴露 |
| 2 | 「本类不包括其他」排除掉所有类别 | 虚指词被当成可匹配类别词 | 一条措辞含糊的目录说明会废掉整个子目录 |
| 3 | 内存 SQLite 单测第一次 insert 就炸 | SQLite 只对 `INTEGER PRIMARY KEY` 自增 | 不修则这层永远没法测 |
| 4 | `version_at("2020-01-01")` 返回 `None` | 用 `status == CURRENT` 过滤，而 `status` 描述的是"现在" | **版本时效这个核心卖点直接失效** |
| 5 | 门控指标 n=4，全部样本都没走到闸门 | 闸门放在槽位检查**之后** | **评测完全测不出来**——264/272 条在到达闸门前就已转成追问 |

第 4 个和第 5 个是最有价值的产出：都不是拼写错误，而是**语义/顺序错误**。

- 第 4 个：一个现在标为 `SUPERSEDED` 的法规版本，在它自己的生效窗口内就是当时的现行版。
  按状态过滤会让"按提问时点检索法规"整个功能失效——而那恰恰是 P1 存在的理由。
- 第 5 个：判"是不是医疗器械"只需要预期用途，不需要接触类型/有无源。
  把闸门放在槽位检查后面，等于**先要求用户回答一个和当前问题无关的问题**。
  这个 bug 只有跑真实评测才会暴露，单测和手工试都发现不了。

详见 `packages/mc-domain/README.md` §1.2 与 `docs/evaluation/README.md`。

## 9. 下一步

按评测结果排出的顺序，不是按功能好做程度：

1. **接线 LLM 槽位抽取** — 覆盖率 1.7% → 目标 >60%。这是唯一的 P0
2. **Ⅲ 类的信号问题** — 决策策略（α）只能挪取舍；上限要靠向量检索 + 领域特征来提
3. 重跑端到端评测，此时类别 Top-1 才第一次有意义
4. 闸门换成语义判定 + 人工复核，用同一台评测机验证特异度
5. 补目录的排除说明（目录库不含「本类不包括」），让排除法这一路真正生效
6. 再动 P2

> 顺序不能反：现在任何"功能做得更多"的努力，都无法让评测数字动一下——
> 瓶颈已经明确锁在抽取与 Ⅲ 类召回这两处。
